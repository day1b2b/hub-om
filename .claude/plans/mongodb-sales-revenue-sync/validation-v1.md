## 구조 재심사를 위한 필수 보완 명세

아래는 **결과 품질에 대한 평가나 PASS 부여가 아니다.** Plan의 Core를 완성하기 위해 필요한 조건·변환·측정 규칙이다. 작성자가 이 규칙을 명시한 뒤 S-1~S-3을 다시 판정해야 한다.

### A. 원본 parity와 독립 oracle

- 기준 커밋의 동기화 함수·route 및 감사에 영향을 주는 의존성의 범위를 고정한다.
- oracle은 새 공통 workflow, 새 금액 변환, 새 매칭 helper를 호출하지 않는다.
- 같은 합성 fixture를 독립 초기 상태의 원본PG·newPG·Mongo에 제공한다.
- 비교 대상은 응답 전체, Course 최종값, 변경감사, sync log, 요청 감사, 호출 횟수·순서다.
- 각 조건 행에 입력, 예상 응답, 예상 부작용, 원본 코드 근거, 테스트 ID를 연결한다. 필수 조건 중 매핑 없는 행은 **0개**여야 한다.
- 보안상 의도적으로 바뀌는 오류 문구는 정확한 허용 차이 목록으로 분리한다. 신규 backend끼리만 일치하거나 차이를 통째로 제거한 비교는 원본 parity 증거로 인정하지 않는다.

### B. 상태·부작용 조건표

최소한 다음 조건을 별도 행으로 확정해야 한다.

| 조건 | 원본에서 확인한 동작 |
|---|---|
| 설정 없음 | `configured=false`, `applied=false`; source 호출 전 반환, 업무 DB·sync log 접근 없음 |
| reader `failed` | `configured=true`, 빈 결과, `applied=false`; 업무 DB·sync log 접근 없음 |
| 정상 preview | Course 조회·변경 계산; 업무 갱신·sync log 생성 없음 |
| partial preview | 미리보기 계산 유지; apply 차단 안내는 추가하지 않음 |
| partial apply | 미리보기 계산 유지, `updatedRows=0`, `applied=false`; 차단 안내 추가, sync log 시도 |
| 정상 apply, pending 없음 | 업무 갱신 없음, `applied=true`, `updatedRows=0`; sync log 시도 |
| 정상 apply, pending 있음 | pending 순서로 일괄 갱신; 성공 시 `updatedRows=pending.length`, sync log 시도 |
| 업무 트랜잭션 실패 | 예외 전파; 뒤의 sync log 코드에 도달하지 않음 |
| sync log 실패 | 이미 정해진 업무 결과·응답을 변경하지 않음 |

“저장 없음”은 **업무 함수 범위**로 한정해야 한다. 실제 GET/POST는 별도의 요청 감사 기록을 시도할 수 있다.

원천 레코드 필터, 코스ID 정규화, 정규화된 resolution 키 충돌, null 금액, 미매칭, 복수 Course, 동일 금액 다중 딜, 서로 다른 금액의 네 가지 모드, 중복 원천도 각각 입력과 기대 카운터를 명시한다. `matchedCourseIds`와 `updatedRows`를 고유 ID 개수로 임의 변경하지 않는다.

### C. Decimal과 재실행

계획에 다음 변환 경로를 각각 적어야 한다.

`원천 JS number → effectiveRevenue → 응답 after / revenueRaw / DB 저장 decimal`

- `revenueRaw`의 원본 규칙은 `String(update.revenue)`다. 저장 decimal의 두 자리 문자열로 대체하지 않는다.
- 합성 입력에 `0`, 음수, `1.004`, `1.005`, `1.006`, 음수 반올림 경계, `0.1 + 0.2`, `999999999999.99`, 범위 초과·반올림 후 범위 초과를 포함한다.
- 비유한 값 등 계약 밖 입력은 허용 여부와 실패 경계를 따로 정의한다.
- 실제 PG 변환 결과를 확인한 뒤 반올림 방식·범위 검사 순서·Mongo 변환 알고리즘을 확정한다. 예상값을 새 구현에서 생성하지 않는다.
- 응답값, raw 문자열, 저장값, 재실행 action·카운터를 별도로 비교한다. 허용 오차로 금액 차이를 숨기지 않는다.
- 아직 실측하지 않은 경계값의 기대 결과는 미정으로 기록한다. 공통 Mongo codec을 완화하여 통과시키지 않는다.

### D. 순서와 복수 매칭

- source 레코드 순서, 중복 횟수, pending 쓰기 순서는 보존한다.
- 정규화 허용 대상을 **필드 경로 단위**로 나열한다. 응답 배열 전체 정렬이나 중복 제거를 포괄 허용하지 않는다.
- 같은 초기 매출에 원천 금액 A→B와 B→A를 각각 넣어 최종 저장값, 응답 before, 갱신 횟수를 비교한다.
- 복수 Course의 무정렬 조회는 순서 비보장으로 명시하되, 이름·금액·action 연결과 모든 매칭 행의 반영은 비교에서 제외하지 않는다.
- `matched[0]` 기반 표시 이름은 조회 첫 행과 일치하는지 검증한다. backend 간 이름 차이를 허용한다면 정확한 필드와 이유를 명시하고, 완전 동일 응답이라고 보고하지 않는다.

### E. 경합과 재시도

- 실제 경쟁 writer와 barrier를 이용해 읽기·쓰기 순서를 고정한다. 시간 지연만으로 경합을 추정하지 않는다.
- 최소 시나리오는 수동필드 변경 선행/후행, 매출 변경 선행/후행, 트랜잭션 충돌 후 재시도다.
- 무관한 수동필드 손실 **0개**, 허용 목록 밖 필드 변경 **0개**를 요구한다.
- 응답 before·pending은 원본 조회 snapshot 규칙을 유지한다. 재시도 때문에 업무 결정을 재계산하지 않는다.
- 감사의 이전 값은 실제 쓰기 시점의 행과 원본 감사 규칙을 기준으로 확정한다.
- 재시도 가능 오류, 전체 제한 시간, 재시도 종료 결과를 명시한다. driver의 재시도 판단 전에 오류 정보를 제거하지 않는다.
- 재시도로 인한 추가 커밋·감사 중복 **0건**을 요구하되, 원본의 의도적인 중복 원천 갱신과 구분한다.
- “후행 쓰기 우선”은 요청 시작순서가 아니라 검증에서 통제한 실제 쓰기 순서로 정의한다.

### F. 원자성과 감사 실패 경계

- 업무 갱신과 변경감사는 동일 트랜잭션에 포함한다.
- 두 번째 업무 갱신 실패, 변경감사 삽입 실패를 각각 주입한다. 해당 시도의 부분 업무 반영·부분 변경감사 잔존은 모두 **0건**이어야 한다.
- sync log 실패는 업무 커밋을 되돌리지 않는다.
- 요청 감사 실패는 업무 결과와 HTTP 응답을 바꾸지 않으며 PG fallback도 발생시키지 않는다.
- 무변경·반복 갱신의 감사 건수는 pending 개수로 추정하지 않고 원본 감사 조건으로 결정한다.
- sync log 상세의 배열별 최대 **500개** 제한과 전체 집계값을 구분하여 대조한다.

### G. 실제 API와 scope 경계

- 내부 `handle`만이 아니라 실제 export된 `GET`, `POST`를 통과하는 검증을 정의한다.
- admin, 비관리자, 정상 secret, 잘못된 bearer+admin, 잘못된 bearer+비관리자, 빈/잘못된 JSON, 유효·무효 resolution을 포함한다.
- 원본 기준: 인증 실패 **403**, 설정 없음 **400**, configured 상태의 failed/partial 반환은 정상 반환 경로에서 **200**, throw는 **500**이다. 임의로 상태 코드를 개선하지 않는다.
- 명시 scope에서 source·업무 repository·requestActivity 각각의 누락을 검증한다. 알림 관련 필수 의존성과 누락 검사 시점도 확정한다.
- 금지된 PG 초기화·실원천·실Slack 호출은 **시도 횟수 0회**를 요구한다. 실제 호출 실패나 우연한 환경변수 미설정은 격리 증거가 아니다.
- 알림 조건은 cron POST의 오류·미설정·미반영이며, 성공·GET·일반 admin 호출은 알림 없음이다.
- “실제 API”는 실제 route/wrapper를 뜻한다. 실Salesmap·Slack 접근이나 운영 DB 사용을 요구하지 않는다.

### H. PII·암호화·오류 비노출

- 저장 검사는 기존 privacy 정책의 대상 필드별로 수행한다. 모든 이름·업무 문자열을 임의로 같은 암호화 대상으로 취급하지 않는다.
- 합성 식별 문자열을 actor, source 오류, driver 오류 등에 넣고 응답 오류·console·알림·평문 저장 위치에서 노출 **0건**을 확인하도록 정의한다.
- 허용된 preview 이름은 정상 업무 응답으로 별도 검증한다. 오류 비노출을 위해 정상 결과를 삭제하지 않는다.
- 안전 오류의 코드·문구와 적용 채널을 표로 고정한다. `issues`와 Slack 오류 문구도 포함한다.
- 키 누락, 잘못된 키, 암호문 변조, AAD 불일치는 인증 실패로 처리한다. 평문 fallback·빈 결과 대체·부분 업무 반영 **0건**을 요구한다.
- 암호문 무작위성 때문에 원본/newPG/Mongo 암호문 바이트를 동일성 기준으로 삼지 않는다. 정책 준수·복호화 후 의미를 비교하고, 수정 대상이 아닌 기존 필드의 보존은 별도로 확인한다.

### I. 전체 검증과 완료 증거

- `npm test`, Mongo 통합 묶음, 실제 합성 PG/Mongo/handler 검증, `npm run typecheck`, `npm run lint`, `npm run build`의 정확한 실행 범위를 적는다.
- 테스트 ID별 실행·통과·실패·skip·미실행을 구분한다. 전체 묶음과 개별 실행의 동일 테스트를 중복 집계하지 않는다.
- 필수 검증의 실패·skip·미실행이 하나라도 있으면 전체 완료를 선언하지 않는다. “차단 사항 명시”는 보고 완료일 뿐 제품 검증 PASS가 아니다.
- 기존 경고는 기준 상태와 대조하고 신규 오류·경고를 분리한다.
- 결과에는 실행 코드 SHA, 명령, 종료 코드, 테스트 수, 독립 리뷰 지적사항과 해소 여부를 연결한다.
- 자원 정리는 이번 실행이 만든 합성 자원으로 한정하고 소유 증거를 남긴다.
- feature/총괄 통합, 원격 SHA, 미커밋 상태와 전체 이전 미완료 범위를 인계 항목으로 구분한다.
- 이번 읽기 전용 검토에서는 위 실행·정리·통합을 수행하지 않는다.
