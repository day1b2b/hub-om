# 개인정보 암호화 후속 계획

## 범위와 명확성
목표/이유/성공 기준/제약 4/4 명확. PR #599를 보존한 독립 브랜치에서 DB 없는 후속 보완을 수행한다. 기존 초안 보존과 충돌하는 브라우저 정책은 총괄 지시로 보류한다. 운영 전환 완료를 주장하지 않는다.
R1~R6 모두 해당: 여러 파일, 공통 쿼리 계약, 검색 대안, 보안 영향, 정확성 검증, 총괄 인계. Level 3.

## Plan v1 및 검토 반영
v1: 누락 확인 → 검색 후보 축소 → CLI repository 전환 → 회귀 검증.
읽기 전용 독립 검토에서 NOT의 부분 제거가 누락을 만들 수 있음, OR 빈 분기, 정렬의 전체 payload 복호화 메모리 부담, 필드별 scan 상한을 확인했다.
v2: 관계 조건은 후보 최적화에서 제외. NOT에 보호 조건이 있으면 전체 제외. 정렬은 최상위 findMany/findFirst에서 정렬 키와 PK만 먼저 읽고 선택한 페이지 payload를 조회한다. 중첩 및 호출자 트랜잭션 내 정렬은 기존 단일 조회/제한 유지. 독립 검토의 undefined/빈 AND 반례에 따라 후보 조건 정규화를 추가했다.

## 실행
1. [Core] 모든 scalar 분류 검증과 서버 파일 저장 경로 비교. 신규 결과보고서 여부는 업무 분류, 직원 명단 파일은 암호화 파일 읽기/변환 지원. 원천/메모/첨부/활동 로그는 기존 policy 및 회귀 유지.
2. [Core] 부분검색에는 원래 결과의 상위집합인 업무 조건만 전달. 20,000행 유지, 암호문 byte budget 추가. 이름 정렬은 좁은 projection 후 페이지 payload 조회. 정확 일치는 HMAC 유지.
3. [Core] 실제 기존 코치 토큰 백필 CLI를 암호화 repository로 전환. dry-run과 apply 분리, fixture 검증, 토큰 출력 금지.
4. [Check] 임시 키/격리 fixture로 정확성·경계·오류를 검증하고 lint/typecheck/test/build/schema validate. DB/화면/배포/복구 검증은 미검증으로 구분.

## 대안
- 전체 무제한 복호화: 정확성 가능하지만 CPU/메모리 상한 없어 제외.
- 부분검색 토큰 인덱스: 빠르지만 검색 패턴 누출과 스키마/백필 비용 있어 제외.
- 기존 상한 + 업무 후보 축소/정렬 projection: 범용 대규모 검색은 미해결이나 추가 검색 인덱스 누출 없이 좁은 조회 복원.
