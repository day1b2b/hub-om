# 팀 작업 방식

이 프로젝트는 여러 작업자가 함께 작업합니다. 같은 파일을 동시에 만지지 않도록 기술 레이어가 아니라 제품 워크플로우 기준으로 나누어 작업합니다.

## 권장 역할 분담

- 각자 맡은 대시보드 워크플로우.
- 페이지 단위 UI와 상호작용.
- 워크플로우별 필터, 테이블, 상세 패널, 입력 폼.
- 로딩, 빈 상태, 에러 상태, 권한 상태.
- 담당 워크플로우의 테스트와 완료 기준 확인.

DB 스키마, 권한, 배포, 공통 데이터 계약처럼 여러 작업에 영향을 주는 변경은 데이터/기술 책임자 검토 후 진행합니다.

## OM 작업 범위 예시

실제 담당자는 팀에서 확정하되, 처음에는 아래처럼 나누는 것이 안전합니다.

- 운영 목록, 큐, 필터, 정렬, 선택.
- 운영 상세, 상태 변경, 운영 액션.
- 입력 폼, 검증, OM 보강 입력.
- 요약/리포팅, QA 체크, 전체 문서/데이터 계약 정리.

더 명확한 실제 업무 도메인이 있으면 이 예시는 바꿔도 됩니다. 중요한 것은 각자가 하나의 완성된 사용자 흐름을 맡는 것입니다.

## PR 규칙

- 하나의 PR은 하나의 사용자 동작 또는 하나의 계약 변경을 담습니다.
- PR 제목은 파일명이 아니라 변경 의도를 설명합니다.
- 완료 기준과 검증 결과를 적습니다.
- UI 변경은 앱이 생긴 뒤부터 스크린샷을 포함합니다.
- 스키마 변경은 마이그레이션/전환 메모를 포함합니다.
- 다른 사람 작업이 의존하는 DB/API 변경은 계약 문서 없이 머지하지 않습니다.

## 브랜치 이름

기본 브랜치:

- `main`: 안정 기준 브랜치.
- `dev`: 함께 모으는 통합 브랜치.

실제 작업은 기능 브랜치에서 합니다. 사람 이름이 아니라 작업 종류를 prefix로 사용합니다.

- `feature/20260604-queue-filters`
- `feature/20260604-detail-actions`
- `feature/20260604-enrichment-form`
- `docs/20260604-data-contract`
- `fix/20260604-status-calculation`

`main`과 `dev`에는 직접 커밋하지 않습니다. 자세한 규칙은 [working-rules.md](working-rules.md)를 따릅니다.

## 매일 확인할 것

- 오늘 바뀐 데이터 계약이 있는가?
- 다른 사람 작업을 막는 브랜치나 PR이 있는가?
- 각 OM이 오늘 어떤 워크플로우를 만지는가?
- 두 명 이상 같은 공유 파일을 건드리고 있지 않은가?
- 현재 앱이 동작한다고 증명하는 검증 명령은 무엇인가?

## 충돌 줄이는 방법

- 공통 레이아웃이나 디자인 시스템 변경은 기능 PR과 분리합니다.
- 워크플로우별 컴포넌트는 워크플로우별 폴더에 둡니다.
- 큰 공통 추상화보다 작고 명확한 공통 helper를 우선합니다.
- 기능 개발 중에는 합의 없이 폴더 이동, 타입명 변경, 공통 파일 대규모 수정을 하지 않습니다.
