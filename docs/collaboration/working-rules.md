# 작업 규칙

이 문서는 hub-om 저장소에서 모두가 지켜야 하는 규칙입니다. 비개발자도 Claude Code를 사용해 작업할 수 있으므로, 실수로 배포 브랜치나 데이터를 망가뜨리지 않는 것을 최우선으로 둡니다.

## 브랜치 역할

- `main`: 배포용 브랜치입니다. 실제 사용자에게 보여도 되는 안정 버전만 둡니다.
- `dev`: 배포 전에 여러 작업을 합쳐서 앱이 정상 작동하는지 확인하는 통합 브랜치입니다.
- 기능 브랜치: 실제 개발은 기능 브랜치에서 합니다.

## 실제 작업 브랜치 이름

브랜치 이름은 사람 기준이 아니라 작업 종류와 날짜를 기준으로 만듭니다.

권장 형식:

```text
작업종류/YYYYMMDD-작업내용
```

예:

```text
feature/20260604-queue-filters
feature/20260604-operation-detail
fix/20260604-status-calculation
docs/20260604-data-contract
chore/20260604-project-setup
```

사용할 prefix:

- `feature`: 새 기능.
- `fix`: 버그 수정.
- `docs`: 문서 작업.
- `chore`: 설정, 정리, 빌드 도구, 기타 운영 작업.
- `hotfix`: 배포 브랜치에서 긴급히 고쳐야 하는 문제.

주의: `feature`, `fix`, `docs`, `chore`, `hotfix` 자체를 단독 브랜치로 만들지 않습니다. `feature/...` 같은 하위 이름을 만들 때 Git 내부 경로가 충돌할 수 있기 때문입니다.

## 브랜치 시작 방법

새 기능 브랜치는 기본적으로 `dev`에서 시작합니다.

```bash
git switch dev
git pull origin dev
git switch -c feature/20260604-queue-filters
```

작업 종류 prefix와 작업명만 바꿔서 사용합니다.

## 작업 시작 전 확인

Claude Code는 작업을 시작하기 전에 `CLAUDE.md`의 작업 시작 프로토콜을 먼저 수행합니다. 그 다음 아래를 확인합니다.

- 현재 브랜치가 `main` 또는 `dev`인지 확인합니다.
- `main` 또는 `dev`라면 직접 작업하지 않고 새 작업 브랜치를 만듭니다.
- 작업 전 `git fetch origin`과 `git pull origin dev`를 실행합니다.
- 같은 화면이나 공통 파일을 다른 작업이 수정 중인지 확인합니다.
- 작업 범위와 완료 기준을 확인합니다.
- 관련 문서를 먼저 읽습니다.

## 머지 규칙

- `main`에 직접 작업하거나 직접 머지하지 않습니다.
- `dev`에 직접 작업하거나 직접 커밋하지 않습니다.
- 기능 브랜치에서 작업하고, 확인 후 `dev`로 머지합니다.
- `dev`에서 충분히 확인한 뒤에만 `main`으로 머지합니다.
- `main` 머지는 배포 책임자가 하거나, 팀에서 명확히 합의한 사람이 합니다.

흐름:

```text
dev
  -> 작업종류/날짜-작업명
  -> 테스트/확인
  -> dev
  -> 전체 작동 확인
  -> main
```

## PR 생성 전 Claude Code 체크리스트

Claude Code는 PR을 만들기 전에 아래를 먼저 확인합니다.

- 작업 시작 프로토콜을 수행했는가?
- 앱이 실행되는가?
- 만든 화면이나 기능이 실제로 동작하는가?
- 에러가 콘솔이나 터미널에 남아 있지 않은가?
- 기존 화면이 깨지지 않았는가?
- 데이터 계약을 바꿨다면 문서도 같이 바꿨는가?
- DB, API, 권한, 배포 설정을 건드렸다면 데이터/기술 책임자가 확인했는가?
- 운영 DB에 영향을 줄 수 있다면 DB 쓰기 안전 규칙을 확인했는가?
- 실제 운영 데이터가 수정/삭제되지 않았는가?

앱 스택이 정해진 뒤에는 아래 같은 검증 명령을 실행합니다.

```bash
npm run lint
npm run typecheck
npm run build
```

명령이 아직 없으면 “실행할 검증 명령이 아직 없다”고 커밋 메시지나 PR 설명에 적습니다.

## 데이터 안전 규칙

운영 데이터는 절대 마음대로 수정하거나 삭제하지 않습니다.

금지:

- 실제 운영 데이터 삭제.
- 실제 운영 데이터 대량 수정.
- 원천 데이터의 값 임의 변경.
- 테스트를 위해 실제 고객사/강사/비용 데이터를 덮어쓰기.
- 민감한 실제 데이터를 Git에 커밋.

허용:

- 샘플 데이터 생성.
- 익명화된 fixture 사용.
- 별도 테스트 파일에서 검증.
- 데이터 정규화 규칙을 코드로 작성하되, 실제 원천 데이터에 바로 쓰지 않고 결과를 검토.

데이터 변경이 꼭 필요하면:

1. 어떤 데이터를 왜 바꾸는지 문서화합니다.
2. 변경 전 백업 또는 export를 남깁니다.
3. 데이터 책임자 확인을 받습니다.
4. 테스트 환경에서 먼저 확인합니다.
5. 실제 반영 후 검증 결과를 남깁니다.

운영 DB에 영향을 줄 수 있는 작업은 [db-write-safety.md](../operations/db-write-safety.md)를 따릅니다. 사용자가 백업 확인 여부와 실행 범위를 명시하지 않으면 운영 DB 쓰기 작업을 진행하지 않습니다.

## 데이터 수집/적재 규칙

Claude Code는 엑셀/시트/Gmail/외부 시스템 원천 데이터를 직접 화면에 연결하지 않습니다.

- 원천 데이터는 직접 수정하지 않습니다.
- 수집/적재는 staging 또는 adapter를 거칩니다.
- 정규화 실패 데이터는 버리지 않고 `validation_errors`에 남깁니다.
- 자동 매칭이 불확실하면 확정하지 않고 검토 대상으로 둡니다.
- 적재 결과를 실제 데이터에 write-back하기 전에는 반드시 검토합니다.
- 실제 원천 파일, 원천 분석 문서, 데이터 예시는 Git에 올리지 않습니다.

## 삭제 규칙

Claude Code는 삭제 작업을 신중하게 처리합니다.

- 실제 데이터는 물리 삭제하지 않습니다.
- 삭제가 필요하면 `deleted_at`, `deleted_by`를 남기는 소프트 삭제를 우선합니다.
- 코드나 문서를 삭제할 때도 사용처를 먼저 확인합니다.
- 대량 삭제, 폴더 이동, 파일명 일괄 변경은 단독으로 진행하지 않습니다.

## 파일 위치 규칙

새 파일은 목적에 맞는 위치에 둡니다.

- 화면 기능: `src/features/기능명/`
- 공통 UI: `src/components/`
- 데이터 접근: `src/lib/data/`
- 협업/브랜치/PR 문서: `docs/collaboration/`
- 반복 문제 해결 문서: `docs/troubleshooting/`

임시 파일, 개인 메모, 실제 엑셀 원본은 Git에 올리지 않습니다.

## 화면 작업 규칙

Claude Code는 화면 기능을 만들 때 아래 상태를 함께 고려합니다.

- 로딩 상태.
- 빈 상태.
- 에러 상태.
- 권한이 없을 때의 상태.
- 저장/수정/삭제 성공 또는 실패 피드백.
- 새로고침 후에도 유지되어야 하는 필터/검색/정렬 상태.

화면 문구는 실제 운영자가 이해하는 용어를 사용합니다.

## Claude Code 결과 검토 규칙

Claude Code는 작업 후 스스로 아래를 점검하고 PR 설명 또는 최종 보고에 남깁니다.

- 요청한 범위 밖의 파일을 바꾸지 않았는가?
- 새 DB 필드나 상태값을 임의로 만들지 않았는가?
- 실제 데이터를 수정하지 않았는가?
- 불필요한 의존성을 추가하지 않았는가?
- 에러를 숨기거나 검증 실패를 무시하지 않았는가?
- 미결정 사항을 비공개 계약 문서 또는 이슈에 남겼는가?

## Claude Code 사용 규칙

Claude Code에 작업을 맡길 때도 아래 규칙을 그대로 적용합니다.

- `main`이나 `dev`에 직접 커밋하지 말라고 지시합니다.
- 작업 브랜치 이름을 명시합니다.
- 참고해야 할 문서를 명시합니다.
- 완료 기준과 검증 명령을 명시합니다.
- 데이터는 수정/삭제하지 말고 샘플 또는 fixture로 작업하라고 명시합니다.

좋은 요청:

```text
현재 브랜치 feature/20260604-queue-filters에서 작업해줘.
비공개 데이터 계약을 기준으로 운영 목록 필터 UI만 구현해줘.
실제 데이터는 수정하지 말고 fixture나 adapter를 통해 읽게 해줘.
작업 후 lint/typecheck 가능 여부를 확인하고 결과를 알려줘.
```

## PR / 리뷰 안내 규칙

Claude Code는 모든 변경을 가능하면 PR로 공유합니다. PR을 만든 뒤에는 요청자가 그대로 따라 할 수 있도록 확인 방법을 자세히 안내해야 합니다.

Claude Code가 PR 생성 후 반드시 알려야 하는 것:

- PR 링크.
- 대상 브랜치가 `dev`인지 확인하라는 안내.
- 확인할 화면 주소, Preview 주소, 또는 로컬 실행 주소.
- 화면에서 확인할 동작 목록.
- 실행한 검증 명령과 결과.
- 실패하거나 확인하지 못한 항목.
- 문제가 있으면 댓글을 남기는 방법.
- 문제가 없으면 머지하는 방법.
- `main`에는 직접 머지하지 말라는 경고.

Claude Code가 PR 설명에 반드시 포함해야 하는 것:

- 변경 목적.
- 변경 파일.
- 확인한 동작.
- 실행한 검증 명령.
- 실패하거나 실행하지 못한 검증.
- 남은 리스크.
- 데이터 계약, 스키마, 권한, 배포 설정 변경 여부.

## PR 확인 방법

PR을 확인하는 사람은 아래 순서대로 확인합니다.

1. Claude Code가 알려준 PR 링크를 엽니다.
2. PR 제목과 설명을 읽습니다.
3. 대상 브랜치가 `dev`인지 확인합니다.
4. `Files changed` 탭을 눌러 어떤 파일이 바뀌었는지 확인합니다.
5. 화면 변경이 있으면 Claude Code가 알려준 주소로 접속합니다.
6. 안내된 확인 항목을 하나씩 확인합니다.
7. 문제가 있으면 PR 화면 아래 댓글창에 무엇이 이상한지 적습니다.
8. 문제가 없으면 `Merge pull request` 버튼을 누릅니다.
9. 다음 화면에서 `Confirm merge`를 누릅니다.
10. 머지 후 `Delete branch` 버튼이 보이면 눌러도 됩니다.

## PR 확인자 체크리스트

PR을 확인하는 사람은 아래를 다시 확인합니다.

- PR 대상 브랜치가 `dev`인가?
- PR 설명에 변경 목적, 검증 결과, 남은 리스크가 적혀 있는가?
- 새 열린 결정이 생겼다면 PR 설명에 표시되어 있는가?
- PR 머지를 막는 열린 결정이 남아 있지 않은가?
- 앱 또는 Preview 주소가 열리는가?
- 안내된 화면/동작이 실제로 작동하는가?
- 기존 화면이 깨지지 않았는가?
- 콘솔이나 화면에 명확한 에러가 없는가?
- 실제 운영 데이터 수정/삭제가 포함되어 있지 않은가?
- 데이터 계약, 스키마, 권한, 배포 설정 변경이 있다면 필요한 검토가 끝났는가?
- 이해하지 못한 변경이 없는가?
- Claude Code가 작업 범위 밖의 파일을 바꾸지 않았는가?
- 열린 결정이 필요한 항목이 문서화되어 있는가?

주의:

- 대상 브랜치가 `main`이면 머지하지 않습니다.
- 검증 실패가 있으면 머지하지 않습니다.
- 실제 운영 데이터 수정이 포함되어 있으면 머지하지 않습니다.
- PR 머지를 막는 열린 결정이 있으면 머지하지 않습니다.
- 이해하지 못한 변경이 있으면 머지하지 말고 댓글로 물어봅니다.

댓글 예시:

```text
운영 목록 화면에서 상태 필터를 `진행중`으로 선택하면 결과가 비어 보입니다.
기대 동작은 진행중 운영 건만 보이는 것입니다.
확인 주소: http://localhost:3000/operations
```

```text
PR 설명에는 `course_id` 정규화만 바꿨다고 되어 있는데,
Files changed에서 아카이빙 상태 계산 파일도 바뀐 것 같습니다.
왜 같이 바뀌었는지 설명 부탁드립니다.
```

## 공통 파일 수정 규칙

아래 파일은 여러 사람 작업에 영향을 주므로 조심해서 수정합니다.

- DB 스키마 문서.
- 데이터 계약 문서.
- 공통 타입.
- 공통 repository/interface.
- 라우팅/layout.
- 인증/권한 로직.
- 공통 UI 컴포넌트.

공통 파일을 바꿀 때는 작업 전후로 왜 바꿨는지 남기고, 다른 사람 작업에 영향이 있는지 확인합니다.

## 작업 중단 / 이어받기

Claude Code는 작업을 끝내지 못하고 멈출 때 아래를 남깁니다.

- 현재 브랜치.
- 하던 작업.
- 완료된 것.
- 남은 것.
- 실행한 명령.
- 실패한 에러.
- 다음 사람이 확인해야 할 파일.

가능하면 PR 설명, 커밋 메시지, 또는 최종 보고에 남깁니다.

## 공유 방식

Claude Code는 작업 공유 시 아래를 적습니다.

- 무엇을 바꿨는지.
- 어디서 확인하는지.
- 무엇을 눌러보면 되는지.
- 통과한 검증.
- 확인하지 못한 것.
- 머지해도 되는 조건.

## 의존성 추가 규칙

새 패키지나 라이브러리는 마음대로 추가하지 않습니다.

추가 전 확인:

- 꼭 필요한가?
- 기존 도구로 해결할 수 없는가?
- 보안이나 유지보수 리스크는 없는가?
- 팀원들이 설치했을 때 문제 없는가?

새 의존성은 기술 책임자 확인 후 추가합니다.

## 비밀값과 계정 정보

아래 값은 절대 Git에 올리지 않습니다.

- DB 비밀번호.
- API key.
- Google Sheet 토큰.
- GitHub token.
- 고객사별 민감 데이터.
- 내부 계정 정보.

필요한 값은 `.env.local` 같은 로컬 환경 파일에 두고, 예시만 `.env.example`에 남깁니다.

## 작업 중 막히면

막혔을 때는 혼자 큰 변경을 계속하지 말고, 아래 정보를 남깁니다.

- 어떤 브랜치에서 작업 중인지.
- 어떤 문서를 기준으로 했는지.
- 어떤 명령을 실행했는지.
- 어떤 에러가 났는지.
- 내가 기대한 동작과 실제 동작이 무엇인지.

이 정보가 있어야 다른 사람이 이어서 확인할 수 있습니다.
