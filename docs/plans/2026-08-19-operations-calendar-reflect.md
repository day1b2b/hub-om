## 1. 목표 & 원칙

운영현황(hub-om DB)에 강의 일정이 **등록/수정/취소**되면 → ①사이트 과정 캘린더 ②내 대시보드 ③구글 캘린더 세 곳에 반영.

**원칙 (반드시 지킬 것)**
- 일정의 **생성·취소는 운영현황에서만**. 사람이 공용 캘린더에 일정을 직접 만들 수 없어야 한다.
- 구글 캘린더에서 담당 매니저가 고칠 수 있는 것은 **초대받은 자기 회차의 날짜·시간뿐**. 그 변경은 운영현황으로 **역반영**한다.
- 그 외 필드(제목·장소·참석자·설명)와 사이트 반영 대상(과정 캘린더·내 대시보드)은 **읽기 전용**. 캘린더에서 바꿔도 다음 동기화에서 운영현황 값으로 되돌린다.

> 개정 배경(2026-08-19): 처음 스펙은 "대상에서 수정 불가·역반영 없음" 단방향이었다. 이후 논의에서 현장 사정으로 매니저가 시간을 조정하는 일이 생기고, 그 수정도 운영현황에 반영되어야 정합성이 유지된다는 쪽으로 맥락이 바뀌었다(이혜림 제안 → 2026-08-19 확정).

## 3. 확정 결정 (D1~D5)

| # | 결정 |
|---|---|
| D1 색상 | 담당 OM == 현장운영 OM → 🟢 초록(기본/과반). 다르면 → 🟠 주황. (**사이트 캘린더 한정**) |
| D2 내 대시보드 | 로그인 사용자가 **담당 OM이거나 현장운영 OM인 일정만**(내 것만) |
| D3 구글 참석자 | **담당 OM + 현장운영 OM 둘 다** 초대 |
| D4 취소 | 이벤트 **삭제** |
| D5 방식 | **B2B 전용 구글 계정 OAuth로 "초대(attendee)"**. 서비스계정 아님(초대 위해). 개인 캘린더에 뜨고, 주최자=B2B(파트 캘린더 소유) |
| D6 수정 권한 | 초대받은 매니저는 **자기 회차 이벤트만** 수정 가능. 이벤트 생성 시 **`guestsCanModify: true`**. **캘린더 공유 권한(ACL)은 부여하지 않는다** — writer를 주면 파트 전체 회차 수정·삭제와 신규 일정 직접 생성이 열려 D6·원칙이 깨짐 |
| D7 역반영 필드 | **날짜·시간만** 운영현황에 반영. 제목·장소·참석자·설명은 hub-om 소유 → 캘린더에서 바뀌어도 다음 동기화에서 원복. (구글은 필드별 권한이 없어 이 제한은 코드로만 강제 가능) |
| D8 캘린더에서 삭제 | **캘린더에서의 삭제는 hub-om에 반영하지 않는다 — 무조치.** 역반영하는 것은 날짜·시간 **수정**뿐이다. 10분 스케줄은 원본이 사라져도 되살리지 않고 DM도 보내지 않는다. **단, 사람이 hub-om에서 그 회차를 저장하면 정방향 반영이 지워진 이벤트를 다시 만들고 초대를 다시 보낸다**(2026-09-04 — 잘못 지운 일정을 되살리는 유일한 길. 사람의 명시적 행동이라 자동 복구의 문제가 없다). 근거: 파트 캘린더에는 **OM장 등 편집 권한자가 있어** 원본 삭제가 실제로 일어나는데(2026-09-03 확인), 되살리면 사람이 의도해서 지운 일정이 10분 뒤 돌아오고 초대 메일(`insert`는 `sendUpdates=all`)과 DM이 반복된다. 회차를 없애는 것은 운영현황에서만 한다(D4). **매핑은 남긴다** — 지우면 다음 정방향 반영이 그 교육일을 새 이벤트로 만들어 되살린다. 흔적은 `[gcal-reverse] 원본 삭제 감지 — 무조치` 로그 |
| D9 초대 거절·삭제한 참석자 | **다시 초대하지 않는다.** 역반영의 원복 patch에는 `attendees`를 넣지 않는다. 안 그러면 지울 때마다 초대가 되돌아와 성가시다 |
| D10 이벤트 단위 | **연속 교육일 구간 1개 = 이벤트 1건.** 9/7·9/8·9/9·9/11이면 `[9/7~9/9]` + `[9/11]` 2건. 기간 하나로 묶으면 쉬는 날까지 일정이 잡히고, 하루씩 쪼개면 초대·변경 메일이 날짜 수만큼 나간다. 접수 알림 표기(`26.09.07~09, 11`)와 같은 묶음 단위다. 대가: 캘린더에서 여러 날 띠로 보이고 하루 시간대는 일정을 열어야 보인다 |
| D11 초대 메일 | 생성(`insert`)·취소(`delete`)는 메일을 보내고, **수정(`patch`)은 참석자 목록이 실제로 달라졌을 때만** 보낸다. 이 서비스는 요청 접수 시 이벤트를 먼저 만들고 **나중에** OM을 배정하므로 초대 메일이 나가는 시점이 `insert`가 아니라 `patch`다 — patch를 전부 조용히 만들면 초대가 아예 안 간다. 담당·현장 OM이 같은 사람이면 두 번째 patch에서 목록이 그대로여서 메일이 중복되지 않는다 |
| D12 사람 수정 판정 | **표식 비교(2026-09-04~).** hub-om은 이벤트 날짜·시간을 쓸 때마다 같은 patch에 `extendedProperties.private.hubOmSchedule`(자기가 쓴 날짜·시간 키)을 남긴다. 이벤트의 현재 날짜·시간이 표식과 **다르면 사람이 고친 것** → 언제 고쳤든 운영현황에 반영. **같으면** hub-om이 쓴 그대로 → 운영현황과 다르다면 정방향 쓰기가 안 닿은 것이니 캘린더를 되돌린다. 시각 차를 보지 않으므로 "저장 후 2분 안 수정이 되돌아가는" 문제가 없다. **표식이 없는 옛 이벤트만** 종전 규칙(이벤트 `updated` − 회차 `updatedAt` > `CALENDAR_REVERSE_SYNC_MIN_LAG_SECONDS`, 기본 120초)으로 판정하며, 표식은 다음 정방향 반영 때 붙는다 |

> D5 배경: 서비스계정은 도메인 전체 위임(DWD) 없이는 참석자 초대 불가(구글 정책). 그래서 **B2B 실제 계정 OAuth** 채택 → 관리자 DWD 불필요, 초대·수정불가 둘 다 충족.

## 4. 신규 작업 A — 사이트 캘린더 색상

- 과정 캘린더 + 내 대시보드 이벤트 색:
  - `omName === onsiteOmName` (또는 현장운영 없음+담당만) → **초록**
  - `omName !== onsiteOmName` (서로 다른 사람) → **주황**
- **내 대시보드 필터**: 로그인 이메일 == 담당 OM 또는 현장운영 OM (이름/이메일 매칭)인 세션만.
- 범례 표시: 초록=담당·현장 동일 / 주황=담당≠현장.

## 5. 신규 작업 B — 구글 캘린더 쓰기(초대)

### 인증
- **B2B 전용 구글 계정 OAuth** (refresh token 방식). 기존 서비스계정 JWT와 **별개 경로**로 추가.
- env: `GOOGLE_CAL_OAUTH_CLIENT_ID` · `GOOGLE_CAL_OAUTH_CLIENT_SECRET` · `GOOGLE_CAL_OAUTH_REFRESH_TOKEN`
- scope: `https://www.googleapis.com/auth/calendar`
- refresh token → access token 갱신 유틸.

### 반영 단위·위치
- **회차(session) 1건 = 구글 이벤트 1건.**
- 이벤트는 **파트 캘린더**(B2B 계정 소유)에 생성. env 매핑: `GOOGLE_CAL_PART_CALENDARS="1파트:calId,2파트:calId,3파트:calId"`
- **참석자(attendees)** = 담당 OM 이메일 + 현장운영 OM 이메일(`TeamUser`에서 이름→이메일). `sendUpdates=all`.
- **주최자 = B2B 계정**(파트 캘린더 소유).
- **`guestsCanModify: true`** — 초대받은 매니저가 **자기 회차 이벤트만** 수정할 수 있게 하는 유일한 방법(D6).
  - 파트 캘린더 **공유 권한(ACL)은 부여하지 않는다.** `writer`를 주면 파트 전체 회차를 수정·삭제할 수 있고 **새 일정을 직접 만들 수 있어** "생성은 운영현황만" 원칙이 뚫린다.
  - 구글은 필드별 권한이 없다. 즉 게스트는 제목·장소도 바꿀 수 있고, 이 제한은 **역반영 화이트리스트(D7)로만** 지켜진다.
- **`extendedProperties.private`** 에 `hubOmSessionId`(회차 id)와 `hubOmRevision`(마지막 반영 리비전)을 심는다. 역방향 매핑 복구와 에코 루프 차단에 쓴다.
- **`guestsCanInviteOthers: false`는 유지** — 참석자를 임의로 늘리는 것은 계속 막는다.
- 설명(description) 머리말(2026-09-04 교체, `EVENT_DESCRIPTION_INTRO`): "hub-om 운영현황과 연동된 일정입니다. · 날짜·시간을 여기서 옮기면 5분 안에 hub-om에 반영됩니다. · 제목·장소는 hub-om 값으로 되돌아갑니다. 바꿀 일이 있으면 hub-om에서 고쳐주세요. · 이 일정을 삭제해도 hub-om에는 반영되지 않습니다. 회차 취소는 hub-om에서 해주세요." 기존 이벤트는 다음 정방향 반영(hub-om 저장) 때 갱신되며 설명 변경은 메일을 보내지 않는다. **동작(주기·반영 필드·삭제 정책)이 바뀌면 이 문구도 함께 바꾼다.**

### 트리거·동작
- **생성** → `events.insert` → 반환 `eventId` 저장.
- **수정**(날짜/시간/장소/OM 변경) → `events.patch`. 담당/현장 OM 바뀌면 attendees 갱신.
- **취소/삭제** → `events.delete`.

### 매핑 저장 (구현됨)
- 테이블 `calendar_event_links`, 키 `(operation_id, event_date)`. `event_date`는 **연속 구간의 시작 교육일**이다(D10).
- 교육일이 등록되지 않은 옛 회차는 기간 이벤트 1건이고 키는 회차 시작일이다.
- 역반영용 별도 컬럼(`lastSynced*`·`syncToken`)은 **두지 않는다** — 아래 감지 방식이 저장 상태를 요구하지 않는다.

## 5-B. 신규 작업 C — 구글 → 운영현황 역반영 (날짜·시간)

D6/D7로 새로 생긴 경로. **날짜·시간만** 운영현황에 되돌린다.

### 변경 감지
- 파트 캘린더별 **`events.list` + `updatedMin` 시간 창**을 쓴다(`CALENDAR_REVERSE_SYNC_LOOKBACK_MINUTES`, 기본 60분).
  `syncToken`을 쓰지 않는 이유는 저장할 상태가 없어 **마이그레이션이 필요 없고**(마이그레이션은 db-write-safety 정지 대상),
  실행이 한 번 빠져도 다음 창이 겹치면 따라잡기 때문이다. `showDeleted=true`로 취소된 이벤트도 본다.
- 실행은 **Coolify Scheduled Tasks**. 마무리 알림 DM(`lecture-followup-dm`)과 같은 방식으로 `POST /api/sync/calendar-events` 를 주기 호출한다(권장 5~15분).
- 새 API 경로를 만들면 **`src/auth.ts`의 `SYNC_API_PATHS`에 경로를 추가**해야 한다. 빠뜨리면 베어러 요청이 `/sign-in`으로 리다이렉트되고, wget이 그 리다이렉트를 따라가 200을 받아 **스케줄 작업이 "Success"로 표시되면서 실제로는 아무 일도 일어나지 않는다**(마무리 알림에서 실제로 겪은 사고).
- 웹훅(`events.watch`)은 채널 만료 갱신·공개 엔드포인트가 필요해 1차 범위에서 제외한다.

### 반영 규칙
- 이벤트 → 회차 매핑: `calendar_event_links`를 `(calendarId, eventId)`로 역조회한다. 매핑이 없는 이벤트는 hub-om이 만들지 않은 일정이므로 **손대지 않고 `skipped`에 기록**한다.
- **반영 필드는 날짜·시간만**(D7). 교육일이 등록된 회차는 `educationDates`에서 그 구간을 새 구간으로 옮기고(`replaceEducationRun`), `startDate`/`endDate`는 리포지토리가 목록의 최소·최대로 다시 계산한다. 교육일이 없는 옛 회차는 `startDate`·`endDate`·`timeText`를 직접 쓴다.
- 제목·장소가 바뀐 이벤트는 **hub-om 값으로 되돌리는 `events.patch`** 를 보낸다(원복). `attendees`는 넣지 않는다(D9).
- **에코 루프 차단**: 비교 대상이 "이벤트 vs 회차 현재값"이라 반영하면 두 값이 같아져 다음 실행에서 대상이 아니다. 여기에 더해 **표식 비교**(D12)로 hub-om 자기 쓰기와 사람의 수정을 가른다 — hub-om이 쓴 값이 표식으로 남아 있으므로 자기 잔향은 표식과 같고, 사람의 수정은 표식과 다르다. 원복 patch와 운영현황 반영 뒤의 제목·장소 원복 patch도 표식을 함께 쓴다(안 그러면 다음 실행이 그 patch를 사람의 수정으로 본다).
- **충돌**: 이벤트 `updated` vs 회차 `updatedAt`으로 최신이 이긴다. 회차 수정 시각을 모르면(로컬 JSON 저장소) 운영현황을 덮어쓰지 않는다.
- 옮긴 구간이 **다른 교육일과 겹치면** 합치지 않고 실패로 남긴다. 코드가 임의로 정리하면 사람이 의도한 일정을 잃는다.
- 운영현황에서 이미 빠진 교육일의 이벤트는 역반영이 **지우지 않고 건너뛴다**(삭제의 시작점은 운영현황). 다음 정방향 반영이 정리한다.
- **운영 DB 쓰기가 있다.** `docs/operations/db-write-safety.md` 대상 → 쓰기 필드는 교육일·시간으로 고정, 1회 적용 상한(`CALENDAR_REVERSE_SYNC_MAX_APPLY`, 기본 20건) 초과 시 한 건도 적용하지 않고, 변경은 `[gcal-reverse]` 접두어로 이전값→새값을 로그에 남긴다.
- `GET`은 계획 미리보기(쓰기 없음), `POST`가 적용이다. **규칙을 바꾼 배포 직후에는 GET을 먼저 열어 확인한다.**

### 캘린더에서 삭제된 경우 (D8·D9)

삭제의 정상 경로는 **운영현황에서 회차를 취소하는 것 하나뿐**이다(D4). 그 경로로 지워지면 hub-om이 `events.delete`를 호출하고 매핑도 함께 정리한다.

**캘린더 쪽에서 지워진 것은 어느 경우든 hub-om에 반영하지 않는다.** 역반영은 날짜·시간 **수정**만 가져온다.

| 매핑 | 이벤트 | 판정 | 처리 |
|---|---|---|---|
| 없음 | 없음 | 이미 취소된 회차 | 아무 것도 하지 않음 |
| 있음 | 없음 / `status: cancelled` | 사람이 캘린더에서 지움 | **무조치** — 재생성 없음, DM 없음, 매핑 유지, 로그만 |

- 게스트가 **자기 캘린더에서만** 지운 것은 원본이 남으므로 애초에 감지 대상이 아니다.
- **되살리지 않는 이유**: 파트 캘린더에는 OM장처럼 편집 권한을 가진 사람이 있어서 원본 삭제가 실제로 일어난다(2026-09-03 김정선님). 되살리면 사람이 의도해서 지운 일정이 10분 뒤 돌아오고, 그때마다 초대 메일과 담당 OM DM이 반복된다. 코드가 사람의 판단과 싸우게 된다.
- **매핑을 남기는 이유**: 지우면 다음 정방향 반영이 그 교육일을 새 이벤트로 만들어 되살린다. `매핑 있음 + 이벤트 없음`이 이 결정을 그대로 나타낸 상태다.
- 매핑이 남으므로 나중에 hub-om에서 그 회차를 저장하면 사라진 이벤트에 `patch`가 간다. `patchEvent`는 404/410을 오류로 던지지 않고 `"missing"`으로 돌려주고, 정방향 반영은 **그 자리에 이벤트를 다시 만들어 매핑을 새 eventId로 바꾼다**(2026-09-04~). `insert`라 초대 메일이 다시 나간다. 이것이 잘못 지운 일정을 되살리는 정식 경로다 — 운영현황에서 그 회차를 열어 저장하면 된다.
- **흔적은 로그뿐이다.** 아무 처리도 하지 않으므로 `[gcal-reverse] … 원본 삭제 감지 — 무조치 (교육일=…, event=…, calendar=…)`가 유일한 기록이다. 응답의 `skipped`는 스케줄 실행에서 아무도 읽지 않는다. 나중에 "이 일정 왜 캘린더에 없지?"를 이 로그로 찾는다.
- 대가: 다음 hub-om 저장까지 **캘린더와 운영현황이 어긋난 상태가 남는다.** 정리는 사람이 한다 — 회차를 없앨 거면 운영현황에서 취소하고, 일정이 다시 필요하면 운영현황에서 그 회차를 저장한다(정방향 반영이 새로 만든다).
- **D9**: 초대를 거절했거나 자기 캘린더에서 지운 참석자는 다시 초대하지 않는다. 원복 patch에 `attendees`를 넣지 않는다.

## 6. 엣지 케이스 / 주의

- OM 이메일 없으면 해당 참석자 스킵(방어) + 로그.
- 현장운영 미정/없음: 색은 **초록**(담당만), 참석자는 담당 OM만.
- 구글 API 실패: 재시도 + 로그, **운영현황 저장은 실패시키지 않음**(부수작업 격리 — `src/app/api/om-request/route.ts`의 "저장 성공 후 부수작업 try/catch" 패턴 참고).
- 다회차 대량 생성 시 rate limit → 배치/간격.
- 삭제 시 매핑도 정리.
- 파트 캘린더를 OM이 구독하면 초대분과 중복 표시 가능 → 구독 정책 안내(파트 캘린더=조망용, 개인은 초대분).
- 게스트가 **반복 일정 중 한 회만** 수정하면 예외 인스턴스가 생긴다. 회차 1건 = 이벤트 1건 구조라 반복 일정을 쓰지 않으면 발생하지 않는다 → **반복 일정으로 만들지 않는다.**
- 게스트가 시간을 바꾸면 다른 참석자에게 구글이 자동 통지한다. hub-om 슬랙 알림과 겹칠 수 있으니 중복 안내 여부를 확인한다.
- 역반영으로 날짜가 바뀌면 마무리 알림 DM의 D+1·D+7 판정 기준일도 함께 움직인다(같은 `endDate`를 보므로 자동).

## 7. 착수 순서 (권장)

1. **DB**: `session ↔ {calendarId, eventId}` 매핑 + 마이그레이션.
2. **구글 OAuth 쓰기 유틸**: refresh→access, `events.insert/patch/delete`.
3. **매핑 config**: 파트→calendarId(env), OM이름→email(`TeamUser`).
4. **반영 훅**: 운영현황 write 경로(생성/수정/취소)에 이벤트 반영 연결. 생성 시 `guestsCanModify: true` + `extendedProperties` 포함.
5. **사이트 색상**: 과정 캘린더 + 내 대시보드(필터+색).
6. **역반영**(구현·가동 완료): `GET/POST /api/sync/calendar-events`(+ `SYNC_API_PATHS` 등록) → 날짜·시간만 DB 반영, 그 외 필드 원복. Coolify 스케줄 `calendar-reverse-sync`(10분)와 `guestsCanModify: true` 모두 2026-09-04 기준 적용됨.
7. **검증**: B2B 계정으로 생성→담당/현장 OM 개인 캘린더 초대 확인 / hub-om 수정→반영 / 취소→삭제 / **게스트가 개인 캘린더에서 시간 변경→운영현황 반영 확인** / **게스트가 제목·장소 변경→다음 동기화에 원복 확인** / 같은 변경이 왕복하지 않는지(에코) 확인.

### 세팅 중 걸렸던 것 (재작업 시 참고)

- 브라우저 기본 계정이 회사 계정이면 GCP 콘솔·OAuth Playground가 조직 정책에 막힌다. 콘솔 URL에 B2B 계정의 `authuser` 파라미터를 붙여서 접근한다.
- 동의 화면을 **내부**로 만들면 `403 org_internal`이 난다. B2B 계정이 개인 Gmail이라 자동 생성된 조직의 구성원이 아니기 때문. **외부**로 설정해야 한다.
- 외부 + `테스트 중` 상태면 **refresh token이 7일 후 만료**된다. 반드시 **프로덕션 게시**까지 해야 한다.
- 프로덕션 게시 조건은 앱 이름·지원 이메일·**홈페이지 URL**·**개인정보처리방침 URL**·승인된 도메인이다. hub-om의 `/privacy`·`/terms`와 서비스 도메인으로 충족했다. 구글 심사(verification)는 동의 계정이 B2B 하나뿐이라 불필요하다.
- OAuth Playground는 리디렉션이 회사 계정으로 돌아가 실패한다. 클라이언트에 `http://localhost` 리디렉션을 추가하고 로컬에서 코드를 받아 교환하는 편이 확실하다.
