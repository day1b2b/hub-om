---

## 1. 목표 & 원칙

운영현황(hub-om DB)에 강의 일정이 **등록/수정/취소**되면 → ①사이트 과정 캘린더 ②내 대시보드 ③구글 캘린더 세 곳에 반영.

**원칙 (반드시 지킬 것)**
- 일정의 **생성·취소는 운영현황에서만**. 사람이 공용 캘린더에 일정을 직접 만들 수 없어야 한다.
- 구글 캘린더에서 담당 매니저가 고칠 수 있는 것은 **초대받은 자기 회차의 날짜·시간뿐**. 그 변경은 운영현황으로 **역반영**한다.
- 그 외 필드(제목·장소·참석자·설명)와 사이트 반영 대상(과정 캘린더·내 대시보드)은 **읽기 전용**. 캘린더에서 바꿔도 다음 동기화에서 운영현황 값으로 되돌린다.

> 개정 배경(2026-08-19): 처음 스펙은 "대상에서 수정 불가·역반영 없음" 단방향이었다. 이후 논의에서 현장 사정으로 매니저가 시간을 조정하는 일이 생기고, 그 수정도 운영현황에 반영되어야 정합성이 유지된다는 쪽으로 맥락이 바뀌었다(이혜림 제안 → 2026-08-19 확정).

## 3. 확정 결정 (D1~D5)

| # | 결정 |
|---|---|
| D1 색상 | 담당 OM == 현장운영 OM → 🟢 초록(기본/과반). 다르면 → 🟠 주황. (**사이트 캘린더 한정**) |
| D2 내 대시보드 | 로그인 사용자가 **담당 OM이거나 현장운영 OM인 일정만**(내 것만) |
| D3 구글 참석자 | **담당 OM + 현장운영 OM 둘 다** 초대 |
| D4 취소 | 이벤트 **삭제** |
| D5 방식 | **B2B 전용 구글 계정 OAuth로 "초대(attendee)"**. 서비스계정 아님(초대 위해). 개인 캘린더에 뜨고, 주최자=B2B(파트 캘린더 소유) |
| D6 수정 권한 | 초대받은 매니저는 **자기 회차 이벤트만** 수정 가능. 이벤트 생성 시 **`guestsCanModify: true`**. **캘린더 공유 권한(ACL)은 부여하지 않는다** — writer를 주면 파트 전체 회차 수정·삭제와 신규 일정 직접 생성이 열려 D6·원칙이 깨짐 |
| D7 역반영 필드 | **날짜·시간만** 운영현황에 반영. 제목·장소·참석자·설명은 hub-om 소유 → 캘린더에서 바뀌어도 다음 동기화에서 원복. (구글은 필드별 권한이 없어 이 제한은 코드로만 강제 가능) |
| D8 캘린더에서 삭제 | **삭제의 정상 경로는 운영현황뿐**(D4). ①게스트가 **자기 캘린더에서만** 지운 경우 = 본인 화면에서만 사라지고 원본은 유지 → hub-om은 아무 조치도 하지 않고 알림도 보내지 않는다. ②**원본 이벤트가 사라진 경우** = 비정상 → 다음 동기화에서 **재생성 + 담당 OM에게 DM 1회**. 판별은 매핑 기준: 매핑 없음+이벤트 없음 = 정상(취소된 회차), **매핑 있음+이벤트 없음/`cancelled` = 비정상** |
| D9 초대 거절·삭제한 참석자 | **다시 초대하지 않는다.** hub-om이 이후 이벤트를 수정할 때도 거절/삭제한 참석자는 그대로 둔다. 안 그러면 지울 때마다 초대가 되돌아와 성가시다 |

> D5 배경: 서비스계정은 도메인 전체 위임(DWD) 없이는 참석자 초대 불가(구글 정책). 그래서 **B2B 실제 계정 OAuth** 채택 → 관리자 DWD 불필요, 초대·수정불가 둘 다 충족.

## 4. 신규 작업 A — 사이트 캘린더 색상

- 과정 캘린더 + 내 대시보드 이벤트 색:
  - `omName === onsiteOmName` (또는 현장운영 없음+담당만) → **초록**
  - `omName !== onsiteOmName` (서로 다른 사람) → **주황**
- **내 대시보드 필터**: 로그인 이메일 == 담당 OM 또는 현장운영 OM (이름/이메일 매칭)인 세션만.
- 범례 표시: 초록=담당·현장 동일 / 주황=담당≠현장.

## 5. 신규 작업 B — 구글 캘린더 쓰기(초대)

### 인증
- **B2B 전용 구글 계정 OAuth** (refresh token 방식). 기존 서비스계정 JWT와 **별개 경로**로 추가.
- env: `GOOGLE_CAL_OAUTH_CLIENT_ID` · `GOOGLE_CAL_OAUTH_CLIENT_SECRET` · `GOOGLE_CAL_OAUTH_REFRESH_TOKEN`
- scope: `https://www.googleapis.com/auth/calendar`
- refresh token → access token 갱신 유틸.

### 반영 단위·위치
- **회차(session) 1건 = 구글 이벤트 1건.**
- 이벤트는 **파트 캘린더**(B2B 계정 소유)에 생성. env 매핑: `GOOGLE_CAL_PART_CALENDARS="1파트:calId,2파트:calId,3파트:calId"`
- **참석자(attendees)** = 담당 OM 이메일 + 현장운영 OM 이메일(`TeamUser`에서 이름→이메일). `sendUpdates=all`.
- **주최자 = B2B 계정**(파트 캘린더 소유).
- **`guestsCanModify: true`** — 초대받은 매니저가 **자기 회차 이벤트만** 수정할 수 있게 하는 유일한 방법(D6).
  - 파트 캘린더 **공유 권한(ACL)은 부여하지 않는다.** `writer`를 주면 파트 전체 회차를 수정·삭제할 수 있고 **새 일정을 직접 만들 수 있어** "생성은 운영현황만" 원칙이 뚫린다.
  - 구글은 필드별 권한이 없다. 즉 게스트는 제목·장소도 바꿀 수 있고, 이 제한은 **역반영 화이트리스트(D7)로만** 지켜진다.
- **`extendedProperties.private`** 에 `hubOmSessionId`(회차 id)와 `hubOmRevision`(마지막 반영 리비전)을 심는다. 역방향 매핑 복구와 에코 루프 차단에 쓴다.
- **`guestsCanInviteOthers: false`는 유지** — 참석자를 임의로 늘리는 것은 계속 막는다.
- 설명(description) 문구 교체: 현재 `수정은 hub-om에서 해주세요.` → `날짜·시간은 이 일정에서 바로 수정하실 수 있습니다. 제목·장소·담당자는 hub-om에서만 수정됩니다.`

### 트리거·동작
- **생성** → `events.insert` → 반환 `eventId` 저장.
- **수정**(날짜/시간/장소/OM 변경) → `events.patch`. 담당/현장 OM 바뀌면 attendees 갱신.
- **취소/삭제** → `events.delete`.

### 매핑 저장 (신규 DB)
- `session.id → { calendarId, eventId }`. (Operation/Session에 필드 추가 또는 신규 매핑 테이블 + 마이그레이션)
- 역반영에 쓸 값도 같이 저장: `lastSyncedStart` · `lastSyncedEnd`(hub-om이 마지막으로 밀어넣은 값), `googleUpdatedAt`, `syncToken`.

## 5-B. 신규 작업 C — 구글 → 운영현황 역반영 (날짜·시간)

D6/D7로 새로 생긴 경로. **날짜·시간만** 운영현황에 되돌린다.

### 변경 감지
- **증분 동기화 폴링**을 채택한다. 파트 캘린더별 `events.list` + `syncToken`(첫 회는 전체, 이후 변경분만)을 저장·재사용.
- 실행은 **Coolify Scheduled Tasks**. 마무리 알림 DM(`lecture-followup-dm`)과 같은 방식으로 `POST /api/sync/calendar-events` 를 주기 호출한다(권장 5~15분).
- 새 API 경로를 만들면 **`src/auth.ts`의 `SYNC_API_PATHS`에 경로를 추가**해야 한다. 빠뜨리면 베어러 요청이 `/sign-in`으로 리다이렉트되고, wget이 그 리다이렉트를 따라가 200을 받아 **스케줄 작업이 "Success"로 표시되면서 실제로는 아무 일도 일어나지 않는다**(마무리 알림에서 실제로 겪은 사고).
- 웹훅(`events.watch`)은 채널 만료 갱신·공개 엔드포인트가 필요해 1차 범위에서 제외한다.

### 반영 규칙
- 이벤트 → 회차 매핑: 매핑 테이블 우선, 없으면 `extendedProperties.private.hubOmSessionId`로 복구.
- **반영 필드는 시작일시·종료일시만.** 제목·장소·참석자·설명이 바뀐 이벤트는 **hub-om 값으로 되돌리는 `events.patch`** 를 보낸다(원복).
- **에코 루프 차단**: 이벤트의 `updated`/변경값이 `lastSyncedStart/End`와 같으면 hub-om 자신이 만든 변경이므로 무시. 역반영으로 DB를 쓴 뒤에는 `lastSynced*`를 갱신하고 구글로 되돌려 쓰지 않는다.
- **충돌**: 필드 단위 최신 수정 우선(last-write-wins). 같은 회차를 hub-om과 캘린더에서 동시에 고치는 경우는 드물고, 규칙이 단순해야 추적이 된다.
- **운영 DB 쓰기가 생긴다.** `docs/operations/db-write-safety.md` 대상 → 쓰기 필드는 날짜·시간으로 고정(화이트리스트), 변경 이력(누가·언제·이전값→새값)을 남긴다.
- 반영 후 담당 OM·LD에게 슬랙 알림(선택). 기존 알림 유틸(`src/lib/slack/notifySlack.ts`) 재사용 가능.

### 캘린더에서 삭제된 경우 (D8·D9)

삭제의 정상 경로는 **운영현황에서 회차를 취소하는 것 하나뿐**이다(D4). 그 경로로 지워지면 hub-om이 `events.delete`를 호출하고 매핑도 함께 정리한다.

| 매핑 | 이벤트 | 판정 | 처리 |
|---|---|---|---|
| 없음 | 없음 | 정상(이미 취소된 회차) | 아무 것도 하지 않음 |
| 있음 | 없음 / `status: cancelled` | **비정상**(사람이 원본을 지움) | **재생성 + 담당 OM에게 DM 1회** |

- 게스트가 **자기 캘린더에서만** 지운 것은 개인 뷰에서 사라질 뿐 원본이 남으므로 위 표의 "정상" 쪽도 "비정상" 쪽도 아니다. **아무 조치도 하지 않고 알림도 보내지 않는다**(본인이 의도한 행동).
- 재생성 알림 문구 예: `캘린더에서 삭제된 일정을 복구했습니다. 취소는 hub-om 운영현황에서 해주세요.` 발송은 마무리 알림 DM과 같은 경로(`sendSlackDirectMessage`) 재사용. 같은 회차로 반복 알림이 가지 않게 하루 1회로 제한한다.
- **D9**: 초대를 거절했거나 자기 캘린더에서 지운 참석자는 **다시 초대하지 않는다.** hub-om이 이후 이벤트를 수정(patch)할 때도 그 참석자의 상태를 유지한다.
- `guestsCanModify` 게스트가 원본을 실제로 삭제할 수 있는지는 **구현 시 실측 확인**이 필요하다(ACL `writer`라면 확실히 가능하지만 이 스펙은 ACL을 주지 않는다). 어느 쪽이든 위 재생성 규칙이 방어가 된다.

## 6. 엣지 케이스 / 주의

- OM 이메일 없으면 해당 참석자 스킵(방어) + 로그.
- 현장운영 미정/없음: 색은 **초록**(담당만), 참석자는 담당 OM만.
- 구글 API 실패: 재시도 + 로그, **운영현황 저장은 실패시키지 않음**(부수작업 격리 — `src/app/api/om-request/route.ts`의 "저장 성공 후 부수작업 try/catch" 패턴 참고).
- 다회차 대량 생성 시 rate limit → 배치/간격.
- 삭제 시 매핑도 정리.
- 파트 캘린더를 OM이 구독하면 초대분과 중복 표시 가능 → 구독 정책 안내(파트 캘린더=조망용, 개인은 초대분).
- 게스트가 **반복 일정 중 한 회만** 수정하면 예외 인스턴스가 생긴다. 회차 1건 = 이벤트 1건 구조라 반복 일정을 쓰지 않으면 발생하지 않는다 → **반복 일정으로 만들지 않는다.**
- 게스트가 시간을 바꾸면 다른 참석자에게 구글이 자동 통지한다. hub-om 슬랙 알림과 겹칠 수 있으니 중복 안내 여부를 확인한다.
- 역반영으로 날짜가 바뀌면 마무리 알림 DM의 D+1·D+7 판정 기준일도 함께 움직인다(같은 `endDate`를 보므로 자동).

## 7. 착수 순서 (권장)

1. **DB**: `session ↔ {calendarId, eventId}` 매핑 + 마이그레이션.
2. **구글 OAuth 쓰기 유틸**: refresh→access, `events.insert/patch/delete`.
3. **매핑 config**: 파트→calendarId(env), OM이름→email(`TeamUser`).
4. **반영 훅**: 운영현황 write 경로(생성/수정/취소)에 이벤트 반영 연결. 생성 시 `guestsCanModify: true` + `extendedProperties` 포함.
5. **사이트 색상**: 과정 캘린더 + 내 대시보드(필터+색).
6. **역반영**: `syncToken` 저장 → `POST /api/sync/calendar-events`(+ `SYNC_API_PATHS` 등록) → 날짜·시간만 DB 반영, 그 외 필드 원복 → Coolify 스케줄 작업 등록.
7. **검증**: B2B 계정으로 생성→담당/현장 OM 개인 캘린더 초대 확인 / hub-om 수정→반영 / 취소→삭제 / **게스트가 개인 캘린더에서 시간 변경→운영현황 반영 확인** / **게스트가 제목·장소 변경→다음 동기화에 원복 확인** / 같은 변경이 왕복하지 않는지(에코) 확인.

### 세팅 중 걸렸던 것 (재작업 시 참고)

- 브라우저 기본 계정이 회사 계정이면 GCP 콘솔·OAuth Playground가 조직 정책에 막힌다. 콘솔 URL에 B2B 계정의 `authuser` 파라미터를 붙여서 접근한다.
- 동의 화면을 **내부**로 만들면 `403 org_internal`이 난다. B2B 계정이 개인 Gmail이라 자동 생성된 조직의 구성원이 아니기 때문. **외부**로 설정해야 한다.
- 외부 + `테스트 중` 상태면 **refresh token이 7일 후 만료**된다. 반드시 **프로덕션 게시**까지 해야 한다.
- 프로덕션 게시 조건은 앱 이름·지원 이메일·**홈페이지 URL**·**개인정보처리방침 URL**·승인된 도메인이다. hub-om의 `/privacy`·`/terms`와 서비스 도메인으로 충족했다. 구글 심사(verification)는 동의 계정이 B2B 하나뿐이라 불필요하다.
- OAuth Playground는 리디렉션이 회사 계정으로 돌아가 실패한다. 클라이언트에 `http://localhost` 리디렉션을 추가하고 로컬에서 코드를 받아 교환하는 편이 확실하다.
