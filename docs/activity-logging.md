# 활동 기록 운영·개발 안내

## 수집 범위

- API 요청: 등록된 101개 HTTP 메서드의 사용자 이메일·이름, 실행 주체, 경로 템플릿, 실제 HTTP 메서드, 응답 상태, 처리 시간, 서버 생성 요청 ID, 완료 시각.
- 변경 이력: 22개 업무 테이블의 실제 생성·수정·삭제·복구. 대상 종류·ID, 변경 필드, 명시적으로 허용한 이전·이후 값, 사용자 및 요청 ID.
- 수동 동기화와 토큰 요청도 API 로그에 남는다. 동기화가 업무 테이블을 바꾸면 동일한 정책으로 변경 이력이 남는다. 기존 sync log는 상세 작업 결과를 계속 담당한다.
- 토큰 요청은 인증 방식의 표시이며, 특정 사람 또는 토큰 인증 성공을 의미하지 않는다. 응답 상태와 함께 확인한다. 다른 브라우저 세션 사용자에게 토큰 요청을 잘못 귀속하지 않는다.
- 이름·업무 이메일·담당자·일정·상태 등 업무 추적에 필요한 필드는 허용 목록에 명시했다. 개인정보 프로필, 자유 입력 메모·본문·피드백, 링크, 접근 토큰은 원본 값을 복사하지 않고 변경 여부만 남긴다. 요청/응답 본문, 쿼리 문자열, 쿠키, IP, 사용자 에이전트는 수집하지 않는다.
- 토큰 재발급은 해당 API 요청 및 access_token 필드 변경으로 확인한다. 토큰 값은 저장하지 않는다.
- 필드 비교 후 마스킹·길이 제한을 적용한다. 500자를 넘는 허용 값은 미리보기와 truncated 표시만 저장한다. 같은 값 저장은 변경 이력을 만들지 않는다.
- 기존 코치 수정 이력 화면은 호환성을 위해 유지한다. 기존 EDIT_HISTORY 행 자체의 생성을 공통 이력에 다시 기록하지 않는다. 과거 이력의 역추적·이관·민감 값 정리는 포함하지 않는다.

인증 프로토콜/상태 검사 및 기존 미추적 캘린더 개발용 API는 제외한다. 미들웨어에서 API에 도달하기 전에 차단된 요청, 페이지 렌더링, 스트리밍 응답 완료 이후의 오류, CLI/직접 SQL 작업, 로컬 JSON 저장 변경은 수집하지 않는다. API 로그는 클릭·체류 시간·실제 사용자 작업량 지표가 아니다. API 응답 200 안에 부분 실패를 담는 기존 기능은 로그에서도 HTTP 200이며, 개별 변경 및 기존 작업 로그로 확인한다.

## 저장 일관성

API의 withActivity가 서버 인증 정보와 요청 ID를 AsyncLocalStorage에 보관한다. Next.js의 라우트별 번들과 전역 Prisma 캐시가 같은 저장소를 쓰도록 저장소도 프로세스 전역으로 공유한다.

Prisma 어댑터는 단독 쓰기를 트랜잭션으로 감싸고, 기존 콜백 트랜잭션에는 요청 정보를 transaction-local PostgreSQL 설정으로 전달한다. DB의 AFTER 트리거가 OLD/NEW를 비교하므로 별도의 사전 SELECT가 필요 없고 동시 업데이트에서도 실제 저장 직전 값을 기록한다. 각 변경과 그 이력은 같은 트랜잭션으로 커밋·롤백된다. 이력 쓰기가 실패하면 해당 업무 쓰기도 실패한다. migration 없이 쓰기를 실행하면 명시적으로 실패한다.

API 로그는 업무 처리 후 제한된 대기 시간 안에 저장하며 실패해도 업무 응답을 실패로 바꾸지 않는다. 서버의 `[activity] API request log write failed` 및 `[activity] retention cleanup failed` 로그로 실패를 확인한다. 예외 객체나 입력값은 이 오류 로그에 복사하지 않는다. 프로세스 중단에 따른 API 로그 누락 가능성은 남아 있다.

기존의 여러 독립 저장을 API 전체의 한 트랜잭션으로 바꾸지는 않는다. 일괄 작업에서 일부만 커밋됐으면 그 부분의 이력은 남는다. 동일 requestId로 관련 변경을 찾을 수 있다. 로그가 마지막 응답 상태보다 실제 DB 반영 상태를 더 정확히 설명할 수 있다.

화면에서 오래된 데이터를 덮어쓰는 것을 막는 version 충돌 UI는 이번 범위에 없다. DB 변경 이력의 전후 값 정확성과 사용자 편집 충돌 방지는 별개다. 현재 저장 정책은 유지하면서 실제 반영된 변화를 추적한다.

PostgreSQL 연결은 UTC로 통일했다. 설치된 adapter-pg가 날짜를 오프셋 없는 값으로 직렬화하므로 서버 기본 시간대가 Asia/Seoul인 경우에도 timestamptz 입력·출력·검색 조건이 어긋나지 않게 한다. 화면과 날짜 필터는 Asia/Seoul, 저장 시각은 UTC다.

## 조회와 보관

관리자 메뉴 → 활동 기록 (`/admin/activity`). API 요청과 변경 이력을 사용자·한국 날짜·실행 주체·요청 ID로 필터링할 수 있다. 변경은 작업·대상 종류·대상 ID, 요청은 API 경로·HTTP 실패 여부로 추가 검색한다. 50건씩 `(occurredAt, id)` 커서로 이동한다. 페이지와 조회 API 모두 관리자 권한을 확인한다. 로그는 일반 UI에서 편집·삭제할 수 없다. DB 관리자에 의한 변조까지 막는 외부 불변 감사 저장소는 아니다.

초기 보관 기준은 API 30일, 변경 365일이다. 요청 로그 저장 시 프로세스당 최대 매시간 한 번, 만료된 각 로그를 오래된 순서로 최대 1,000건씩 정리한다. 서비스가 유휴 상태이거나 만료분이 많이 쌓이면 삭제가 지연될 수 있다. 수동 또는 운영 스케줄러에서 `npm run activity:prune`을 실행하면 만료분을 배치로 모두 정리한다. 별도 정기 스케줄러는 이번 변경에서 설치하지 않았다. 이 명령은 설정된 DATABASE_URL에 연결하므로 실행 대상을 확인해야 한다.

## 배포 순서

1. migration SQL 검토: 새 로그 테이블 2개, 함수 2개, 업무 테이블 22개의 트리거를 한 트랜잭션으로 생성한다. 기존 업무 행을 변경하지 않지만 트리거 생성에는 테이블 잠금이 필요하다. 잠금 대기는 5초로 제한했다. 잠금 충돌로 실패하면 원인을 해소한 후 실패한 migration 상태를 확인·정리하고 재적용한다.
2. 대상 환경에서 `npm run db:migrate:deploy`를 성공시킨다.
3. 새 Prisma Client를 생성한 앱을 배포하고 서버 프로세스를 재시작한다. 기존 개발 서버의 전역 Prisma 캐시만 유지한 HMR에 의존하지 않는다.
4. 테스트 변경을 수행하고, 요청 ID로 API 로그와 변경 이력이 연결되는지 확인한다. 일반 계정의 직접 조회가 403인지 확인한다.

운영 DB에는 아직 이 migration을 적용하지 않았다. 별도 로컬 PostgreSQL에서 전체 migration 체인과 실제 API를 검증했다.

## 새 API·필드·테이블 추가

- API: HTTP 메서드를 withActivity로 감싸고 route-policy.json에 추가한다. 제외 시 구체적인 이유를 기록한다. withActivity는 인증을 대신하지 않는다.
- 테이블: field-policy.json에 값 허용/변경 여부 필드를 명시하고 새 migration에 트리거를 추가하거나 table-exclusions.json에 제외 이유를 기록한다.
- 필드: 알 수 없는 필드는 DB 트리거에서 기본적으로 값 없이 변경 여부만 남긴다. CI가 정책 미등록을 검출하면 적절한 분류를 추가한다. 허용 목록 수정은 JSON뿐 아니라 새 migration으로 DB의 트리거 인자도 변경해야 한다. 배포된 migration을 수정하지 않는다.
- 쓰기: 공용 getPrismaClient와 모델 delegate 또는 콜백 트랜잭션을 사용한다. 배열형 `$transaction([...])`은 지원하지 않는다. 직접 raw SQL 쓰기가 필요하면 컨텍스트를 설정하는 콜백 트랜잭션 안에서 수행해야 한다. 별도 PrismaClient나 콜백 밖 raw SQL 쓰기는 우회 경로가 되므로 추가하지 않는다.

## 검증

`npm test`는 API별 wrapper 등록, 테이블·필드 정책, 한국 날짜·커서, 요청 메타데이터·실패 처리, 관리자 접근 차단을 검사한다.

실제 DB 테스트는 운영 연결을 허용하지 않는다. 전용 로컬 DB(`activity_test`로 시작하는 이름)에 migration을 적용한 후 다음을 실행한다.

```sh
ACTIVITY_TEST_DATABASE_URL='postgresql://USER@127.0.0.1:PORT/activity_test' npm test
```

DB 테스트는 민감 값 비노출, no-op, 길이 제한, 트랜잭션 롤백, 동시 수정의 실제 이전 값, 이력 실패 시 저장 취소, 삭제·복구·cascade, 요청 간 사용자 정보 격리, 일괄 변경, 만료분 정리를 확인한다. 테스트용 생성 행은 정리한다. 브라우저 검증은 별도 복사본·로컬 DB·개발용 계정으로 수행했다.

2026-09-07 검증 결과: 전체 테스트 372개 통과(격리 PostgreSQL 통합 테스트 포함), lint 오류 0개·기존 경고 7개, Prisma schema validate 통과. 실제 HTTP에서 코치 생성·수정·삭제, 민감 값 비노출, 요청 ID 연결, 50건 페이지 이동, 일반 계정의 403을 확인했다. 브라우저에서 상세 펼치기·탭·페이지 이동·실패 필터·가로 넘침 수정을 확인했다. 전체 typecheck는 이번에 수정하지 않은 src/app/api/calendar/test-event/route.ts 두 곳과 src/app/calendar-test/page.tsx 한 곳의 googleCalendarEventsGranted 타입 오류 때문에 실패하며, 활동 기록 변경 파일의 오류는 보고되지 않았다.

## 별도 비공개 조회 사이트

주소: https://hub-om-activity.hayeonhee.chatgpt.site

별도 소스: `/Users/ga/workspace/hub-om-activity`. Sites 소유자만 열 수 있는 읽기 전용 사이트다. 수집은 기존 hub-om 서버에서 수행하고, 조회 사이트 서버가 `/api/activity-feed`를 호출한다. 브라우저에는 연결 키를 보내지 않으며 CORS 공개나 로그 복제 저장은 하지 않는다.

- 원본 서버 `ACTIVITY_FEED_KEY`와 Sites 런타임 secret에 같은 무작위 키를 설정한다. 키는 원본 `.env.local`에 생성해 두었다. Git이나 화면에 복사하지 않는다.
- 원본 운영 환경에는 동일 키를 Coolify 런타임 비밀값으로 등록하고, migration과 수집/조회 코드를 배포해야 한다. 이 작업만으로 원본 운영 환경이 배포된 것은 아니다.
- 기존 운영 배포 절차: feature → dev PR → main 승격 → Coolify. `RUN_DB_MIGRATIONS=true` 사용 시 컨테이너 시작 전에 migration이 성공해야 한다.
- API 전용 키는 이 피드의 읽기만 허용한다. 로그인 쿠키로 피드를 호출할 수 없다. 키가 미설정이거나 32자 미만이면 503, 인증 실패는 401이다.
- 날짜는 한국 시간 기준 1/7/30/90/365일만 허용한다. 최대 50행, 커서 페이지 이동. 조회와 요약은 하나의 RepeatableRead 트랜잭션으로 읽는다.
- 요약은 기간·사용자 기준이며 표의 세부 필터와 독립적이다. API 기반 사용자/요청 통계는 30일 보관분까지만 제공된다.
- 연결되지 않았을 때는 오류/연결 대기를 표시하며 0건이나 샘플 수치를 표시하지 않는다.

연결 키를 회전할 때는 두 서버를 함께 갱신하고 Sites도 재배포한다. 키를 아는 사람은 개인정보가 일부 포함된 조회 권한을 가지므로 서버 비밀값으로 취급한다.

## 팀용 접속 방식 (2026-09-07 변경)

팀원에게 안내할 주소는 `https://hub-om.skillflo.app/activity`다. 원본 서비스 배포 후 사용할 수 있다. 별도 화면이지만 기존 hub-om과 같은 서버에서 제공하여 회사 Google 로그인 세션을 공유한다. ChatGPT 계정과 ACTIVITY_FEED_KEY는 이 팀용 화면에 필요하지 않다.

- 이번 변경은 UI/경로 연결이며 새 DB 변경은 없다. 앞선 수집 migration과 코드의 운영 배포는 여전히 필요하다.
- 기존 미커밋 변경을 보존해 작업 브랜치에서 진행했다. 원격 dev의 후속 변경은 배포 전 통합 검증이 필요하다.

### 운영 배포 준비 검증

최신 dev 변경을 포함한 독립 작업 폴더에서 통합했다. 새 캘린더 backfill API도 수집 대상에 포함했고, 기존 본문 크기 제한 테스트는 활동 수집 단위 테스트와 분리했다. 테스트 415개(실제 로컬 PostgreSQL 검증 포함)가 통과했으며 lint는 기존 경고 7개만 남았다. 개인 개발용 캘린더 파일을 제외한 배포 소스의 typecheck도 통과했다.

2026-09-07 사용자가 백업 확보 조건의 활동 기록 테이블·트리거 추가와 서비스 배포 진행에 동의했다. 운영 Coolify 접속 및 실행 결과는 배포 완료 시 별도로 확인해야 한다. 배포 전 현재 pending migration 목록을 확인하여 이번 활동 기록 migration 외의 미적용 변경을 임의로 함께 실행하지 않는다.
