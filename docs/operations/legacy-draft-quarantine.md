# 옛 초안 암호화 격리 전환

## 승인된 범위

2026-09-21 사용자가 작성자 정보가 없는 옛 브라우저 초안의 암호화 보존을 승인했다. 원문을 현재 로그인한 계정에 귀속하지 않고, 일반 업무 화면으로 자동 복구하지 않는다. 작성자를 확인할 수 있다는 근거 없는 가정을 사용하지 않는다. 이 기능은 소유권을 복원하는 기능이 아니다.

암호화 보존은 파기와 다르다. 서버 전용 격리 키를 유지하면 저장한 자료의 복호화 가능성을 검증할 수 있지만, 그 내용이 어느 사람의 초안인지는 알 수 없다. 따라서 브라우저에 격리 복호화 키나 원문 조회 API를 제공하지 않는다.

## 데이터 손실 방지 계약

1. 지정된 옛 초안 키만 열거한다. 저장소 키 자체에 이메일이 들어갈 수 있으므로 키와 값 모두 암호화 대상이다.
2. 캡처한 원문을 서버에서 격리 전용 키로 암호화한다. 이름·연락처·메모·링크·원문 키를 화면이나 로그에 출력하지 않는다.
3. 새 암호문을 브라우저 IndexedDB에 덮어쓰지 않는 별도 레코드로 저장한다. 단순 요청 성공이 아니라 트랜잭션 commit을 기다린다.
4. 실제 저장한 레코드를 다시 읽고 검증한다. 복호화된 내용이 최초 캡처와 일치하는지 서버에서 확인하며 원문은 브라우저에 재반환하지 않는다.
5. 평문 삭제 직전에도 원문이 캡처 당시와 같은지 확인한다. 검증 실패·네트워크 실패·원문 변경·용량 부족·키 설정 오류가 있으면 원문을 유지한다.
6. 삭제 후 다시 스캔한다. 옛 코드가 평문을 다시 만들면 전환 대상으로 표시하며 완료 상태를 유지하지 않는다.

키 설정 누락이나 장애 시 평문을 다른 영구 저장소로 복사하는 fallback을 만들지 않는다. 기존 원문과 검증된 암호문을 임의로 정리하거나 만료시키지 않는다. 중복 사본은 유일한 초안의 손실보다 안전하므로 실패 후 재시도로 여러 격리 사본이 남을 수 있다.

## 여러 탭의 전환

localStorage는 같은 origin의 탭들이 공유하지만, sessionStorage는 탭별로 존재한다. 탭을 먼저 닫으면 그 탭에만 있던 등록 재개 정보가 사라질 수 있다.

- 기존 탭은 현재 입력을 저장한 후 **각각 새로고침**해 새 코드로 전환한다. 저장소를 초기화하거나 모든 탭을 먼저 닫지 않는다.
- 각 탭에서 그 탭의 sessionStorage 초안을 먼저 암호화·검증한다. localStorage도 암호화 사본을 먼저 보존한다.
- 모든 관련 탭의 전환을 마친 뒤 나머지 앱 탭을 닫고 마지막 탭에서 공유 평문 제거를 진행한다. 같은 origin의 창·iframe 등 과거 코드를 실행할 수 있는 화면도 이 조건에 포함한다. 전환 중에는 새 앱 창을 열지 않는다.
- 이 확인은 초안의 작성자 확인이 아니라 구버전 코드의 재기록과 삭제 경합을 피하기 위한 운영 조건이다.

**구버전 탭이 없음을 코드만으로 증명할 수는 없다.** 구버전은 새 Web Lock이나 BroadcastChannel에 참여하지 않는다. localStorage의 읽기·비교·삭제 역시 하나의 원자적 연산이 아니다. 그러므로 위 운영 조건 확인 전에는 공유 평문을 자동 제거하지 않는다. 새 Service Worker를 도입해 이 한계가 해결된 것처럼 처리하지 않는다.

## 완료 상태의 의미

| 상태 | 의미 |
| --- | --- |
| 암호화 보존 완료 | 발견한 스냅샷을 영구 저장하고 복호화 일치 검증을 마침 |
| 평문 제거 대기 | 보존됐으나 다른 탭의 전환 등 제거 조건이 충족되지 않음 |
| 현재 검사 범위에 옛 평문 없음 | 현재 브라우저의 공유 저장소와 현재 탭의 세션 저장소에서 대상 키를 찾지 못함 |
| 운영 전환 완료 | 필요한 브라우저·탭·프로필에서 실행과 잔존 여부를 실제 확인함 |

한 탭의 검사 결과로 다른 탭의 sessionStorage나 다른 기기까지 평문이 없다고 단정하지 않는다. 기존 등록 재개 정보의 원문이 사라져도 등록이 성공했다고 간주하지 않으며, 신규 등록을 통한 중복 생성 방지 안내를 유지한다.

## 실행 및 배포 경계

이 작업은 코드와 합성 데이터 검증이다. 실제 브라우저 초안, 운영 DB, 운영 키, Coolify 설정을 변경하지 않는다. 새 의존성과 DB 스키마 변경 없이 구현한다. 실제 전용 키 설정·보관·복구와 기술 검토를 마친 후 배포해야 사용자의 브라우저에서 전환을 실행할 수 있다.

서버 API, 별도 키 보관·회전과 제한된 오프라인 복구 도구는 [서버 계약과 복구 절차](legacy-draft-quarantine-server.md)를 따른다. 암호문은 해당 브라우저에 보관되므로 브라우저 데이터 삭제나 장치 손실에 대한 백업은 아니다.

등록 재개 원문은 일부 회차가 서버에 이미 등록됐을 수 있다. 전환 후에도 개인정보 없는 미확정 표시를 남긴다. 사용자가 운영 현황에서 기존 등록 여부를 확인하고 **옛 등록을 재개하지 않고 새 등록을 시작한다**는 확인을 해야 신규 등록 차단을 해제한다. 이 확인으로 작성자가 증명되거나 격리 사본이 삭제되지는 않는다.

- `npm test`: 701개 통과, 실패 0개, 실제 격리 PostgreSQL을 요구하는 4개 생략.
- `npm run typecheck`, `npm run build`: 통과.
- `npm run lint`: 오류 0개, 기존 무관한 경고 7개.
- 독립 검토: 저장 commit·재읽기·서버 검증·삭제 순서, 계정 변경 중단, 원문 변경 재시도, 등록 미확정 표시와 명시적 새 등록 확인을 검토했다. 전환 관련 21개 테스트를 별도로 실행해 통과했다.
- 실제 Next HTTP 합성 환경에서 7MiB 원문의 봉인과 약 17MiB 검증 요청을 확인했다. 프록시의 기본 body 제한 문제를 두 인증 내장 API의 정확한 경로 예외로 보완했다.
- 실제 제품 UI·native IndexedDB 합성 검사에서 검증 실패·quota 오류 시 원문 유지, 탭 원문 선행 전환, 공유 원문 확인 후 제거, 등록 미확정 표시 유지와 명시적 새 등록, 재로드 후 간결한 완료 표시를 확인했다. [클라이언트 검증 근거와 한계](legacy-draft-quarantine-client.md)에 기록했다.

실제 Google 인증, Coolify 프록시 설정, 운영 키, 운영 브라우저의 기존 자료 전환은 실행하지 않았다. 코드 검증 통과가 실제 사용자 저장소의 평문 제거 완료를 의미하지 않는다.

## 검증 기준

- 저장된 암호문에 원문·원문 키·격리 비밀키가 남지 않으며 일반 계정으로 읽을 수 없다.
- 저장 commit 이전·재읽기 손상·검증 거부·서버 장애·quota·원문 변경 시 삭제하지 않는다.
- 삭제 전 캡처와 실제 보존된 사본의 일치 검증을 우회할 수 없다.
- 기존 사본을 덮어쓰지 않고 재시도할 수 있으며 키 회전 시 과거 사본을 검증할 수 있다.
- 공유 평문은 운영 조건 확인 전 제거하지 않는다. 세션 초안은 해당 탭에서만 전환한다.
- 원문 재생성·다른 탭·저장소 접근 거부를 전체 완료로 표시하지 않는다.
- 기존 네 초안 저장·계정 분리·장애 중 저장·등록 재개 기능의 회귀가 없다.
