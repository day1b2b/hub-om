# MongoDB 이전 백업·최종 전환 준비 및 인계 계획

작성 기준: 2026-09-30, 지정 작업 공간의 공개 문서·코드 정적 확인. 이 문서는 실행 승인이 아니며 아래 절차는 모두 향후 승인된 실행자를 위한 준비 계획이다.

## 1. 확정 범위와 현재 상태

- MongoDB 이전은 필수다. 현재 사용 기능, 개인정보 암호화, 기존 권한과 접근 거부 동작을 유지한다. 신규 제품 개선·의존성·암호화 정책·보존 정책은 추가하지 않는다.
- 데이터 유실은 허용하지 않는다. 독립된 두 저장 위치 A/B에 각각 완전한 복구 세트를 확보하고, 각각 무결성·키 복구·격리 복원·앱 검증을 통과해야 한다. 두 복사본의 존재나 업로드 성공만으로 통과하지 않는다.
- **실제 백업 확인 증거는 현재 0건이다. 실제 백업 존재·완전성·복구 가능성 모두 미확인이다.** 로컬 합성 검증, 과거 shadow 성공 기록, 코드 테스트는 실백업 증거가 아니다.
- 이번 작업은 이 문서만 신규 작성한다. 운영·실원천·키·env·배포 설정·비밀·DB에 접근하거나 변경하지 않고, 네트워크 백업·export/import·복원·연결 진단도 실행하지 않는다.
- 원본 PostgreSQL과 기존 백업·실제 파일은 보존한다. 이전 과정에서 원본 암호화 backfill, 물리 삭제, 정리, 키 교체를 임의 실행하지 않는다.
- 브라우저 임시저장 암호화는 후속 과제로 보존하되 **이번 MongoDB 전환의 선행조건이 아니다.** DB 백업이 브라우저 초안을 포함하거나 보호한다고 주장하지 않는다.

## 2. 확인한 근거와 기존 도구의 한계

운영 안전 기준은 [DB 쓰기 안전](db-write-safety.md), [DB runbook](database-runbook.md), [원천 읽기 계약](source-read-contract.md)을 따른다. 기존 암호화 계약은 [개인정보 암호화](personal-data-encryption.md), 이관 도구 계약은 [shadow transfer](mongodb-shadow-transfer.md)를 참고한다. 문서의 과거 실행 기록은 이번 작업의 실행 결과와 구분한다.

| 읽은 코드 | 확인한 동작 | 전환 준비 시 보완·검증할 경계 |
| --- | --- | --- |
| [백업 API](../../src/app/api/admin/backup/route.ts) | secret 인증 또는 개인정보 접근 가드 후 Prisma로 코치 관련 일부 모델과 최근 archive snapshot 메타데이터 최대 20건을 JSON 응답한다. 여러 조회는 `Promise.all`이다 | 전체 DB 백업이 아니며 단일 시점 보장 트랜잭션, A/B 저장, 파일 checksum, 복원 기능이 이 코드에 없다. 아카이브 원문 행·전체 운영·사용자·공지 첨부 등을 포괄하지 않는다. JSON 응답 자체의 별도 백업 암호화도 없다. 실제 응답 암호화 상태는 미확인이다. Mongo 전환 후 사용 중인 API라면 기존 권한·응답 계약을 유지하는 연결과 검증이 필요하다 |
| [export 진입점](../../scripts/export-mongodb-shadow.ts), [PG source](../../src/lib/migration/postgresShadowSource.ts) | 명시적 실행 조건으로 PG를 읽고 한 연결의 read-only repeatable-read transaction에서 모델을 조회한다. schema/type/PK를 검사한다 | 코드에 등록된 모델만 다룬다. DB 전체 객체·권한·확장·트리거·외부 파일까지 복구하는 PG 전체 백업과 같지 않다. 운영 schema 차이와 실제 원천 모드는 미확인이다 |
| [export writer](../../src/lib/migration/postgresShadowExport.ts), [codec](../../src/lib/migration/mongoDocumentCodec.ts) | 개인정보는 기록 전 기존 정책으로 암호화한다. 새 디렉터리/파일, fsync, 완료 manifest, 모델별 count/digest를 사용한다 | 필드 암호화와 백업 매체 전체 암호화는 별개다. manifest digest는 정렬된 ID·문서 해시의 내용 digest이며 파일 bytes checksum이 아니다. 별도 파일 checksum과 복구 세트 목록 대조가 필요하다 |
| [import 진입점](../../scripts/import-mongodb-shadow.ts), [spool importer](../../src/lib/migration/mongoShadowImport.ts) | 대상 연결 전에 manifest·파일·암호문·순서·건수를 검사한다. 파일당 32 MiB, 모델 파일 합계 128 MiB, 전체 100만 행 제한이 있다 | 운영 규모 수용 여부 미확인. 제한 초과를 일부 누락·무시로 해결하지 않는다. 현재 importer를 그대로 대규모 운영 loader라고 간주하지 않는다 |
| [transfer](../../src/lib/migration/mongoShadowTransfer.ts), [shadow target](../../src/lib/mongodb/shadowTarget.ts) | 별도 shadow namespace에 insert-only. 동일 run 재시도는 동일 내용만 허용하고 대상 재조회·건수·내용·선언된 FK/unique/HMAC unique를 검증한다 | 운영 promotion, 기존 행 갱신·삭제분 적용, PG 역이관 도구가 아니다. 사후 unique 검사는 실제 Mongo 인덱스 설치를 대신하지 않는다. 실패한 부분 namespace를 운영 대상으로 사용하지 않는다 |

현재 schema에는 논리 모델 35개가 있으나 이 숫자를 운영 전체 보존 범위의 증명으로 쓰지 않는다. [Prisma schema](../../prisma/schema.prisma)의 `AnnouncementAttachment.data`는 DB bytes이며 `CoachdbArchiveRow`는 보관 원문이다. 둘 다 범위 누락 없이 검증해야 한다. 외부 첨부·수동 메일 아카이브·서버 파일·비공개 adapter의 실제 사용 여부와 위치는 별도 책임자 확인 대상이다.

기존 도구는 성공해도 `cutoverAuthorized: false`, `liveChangesSynchronized: false`다. sequence는 MVCC 대상이 아니며 export의 `sequenceHighWater`만으로 마지막 채번 상태를 증명할 수 없다. `sequenceValuesRequireFrozenRecheck: true`를 해소할 최종 freeze 재대조가 필요하다. 도구에 운영 복귀 기능이 있다고 해석하지 않는다.

## 3. 복구 세트 목록과 분리 보관

데이터 책임자는 실제 값이 없는 공개 목록과 접근 제한된 비공개 상세 장부를 구분한다. 아래 각 항목의 포함 여부, 담당자, 복구 의존성, 기준 checkpoint를 확인한다. 미사용 판정도 근거를 남기며 누락을 미사용으로 처리하지 않는다.

| 구성 | 반드시 보존·대조할 내용 | 복구 시 확인 |
| --- | --- | --- |
| 원본 PG 복구본 | 전 DB 데이터, 미모델링 객체 포함 목록, schema/migration 상태, sequence의 값·호출 여부·증분, 역할/권한·확장·함수/트리거 등 복원 의존성 | 승인된 전체 백업 방식으로 빈 격리 PG에 복원 가능해야 한다. 필요 로그·복구 시점 의존성을 함께 보존한다 |
| Mongo 이관본 및 운영 시작 후 복구본 | 전체 논리 모델·ID·관계·삭제 상태·감사/원천/오류 기록, ciphertext·HMAC, indexes/validators·채번 상태, 일관성 및 쓰기 checkpoint | shadow spool, 실제 운영용 데이터 배치, Mongo 백업의 역할을 구분한다. 선택된 Mongo 복구 방식이 checkpoint까지의 모든 승인된 쓰기를 보존해야 한다 |
| 첨부·필수 파일 | DB 내 첨부 bytes와 메타데이터, DB 밖 첨부/필수 서버 파일, 실제 사용 중인 수동 아카이브·비공개 adapter/실행 산출물 | 파일 목록·버전·bytes·object count·checksum과 DB 참조를 연결한다. 링크만 저장된 자료를 bytes 백업 완료로 계산하지 않는다. 실원천은 별도 허용 범위 확정 전 읽거나 복사하지 않는다 |
| 복구 코드·구성 | 실행 가능한 코드/산출물 버전, schema/codec/정책 버전, 비밀이 제거된 구성 명세, 기존 권한 매핑과 작업 구성의 복구 절차 | 당시 데이터·암호문과 호환되는 앱을 재현한다. 단순 Git commit만으로 비공개 의존성이 복구된다고 가정하지 않는다 |
| 키·복구용 비밀 설정 | 활성/과거 암호화 키 버전, HMAC 키, 백업 암호화 복구 수단, 필요한 인증·연동 비밀 설정의 안전한 복구 절차 | 데이터 백업과 접근 경계를 분리한 보안 보관. 실제 값은 문서·명령 인자·로그·Git에 남기지 않는다. DB 접근 없이도 승인자가 키를 되찾을 수 있어야 한다 |

A/B 각각 데이터 세트가 완전해야 하며 반씩 나누어 보관하지 않는다. 키·비밀 설정은 데이터 세트에 동봉하지 않는다. A나 B 또는 운영 호스트가 상실되어도 남은 세트와 안전하게 분리된 복구 수단으로 복원 가능한지 각각 시험한다. 키 보관 자체의 단일 장애점도 확인한다. 키와 데이터를 함께 무제한 복제한다는 뜻이 아니며 기존 보안 권한과 보존 기준을 따른다.

## 4. 독립 저장 위치 A/B 책임자 확인표

A/B 후보는 **Google Drive(A)**와 **OneDrive(B)**로 정했다. 외장 SSD는 사용하지 않는다. 로컬 디스크는 백업 세트를 암호화해 생성하거나 격리 복원하는 임시 작업 공간으로만 사용하며 영구 A/B로 계산하지 않는다. 같은 Mongo 클러스터·같은 계정의 `hub-om-shadow-validation`과 `hub-om`도 독립 백업 두 개로 계산하지 않는다.

후보 서비스가 정해졌다는 사실은 독립 백업 완료 증거가 아니다. 실제 계정·접속값·용량·기간, 계정과 삭제 권한의 독립성, 전송·저장 암호화, 비상 복구 권한은 실백업 실행 전에 비공개 장부에서 확인한다. 같은 디스크의 두 폴더, 같은 볼륨의 두 파일, 동일 삭제 권한에 종속된 사본을 독립성 증거로 인정하지 않는다.

| 확인 항목 | A에서 필요한 증거 | B에서 필요한 증거 | 확인 책임 역할 |
| --- | --- | --- | --- |
| 위치와 실패 도메인 | 비공개 위치 참조, 호스트/매체/서비스/계정/지역 등 실제 장애 경계 | A와 공유하는 장애·침해·삭제 경로 분석, A 상실 시 독립 회수 증거 | 인프라·보안 책임자 |
| 저장·전송 암호화 | 실제 적용 방식과 키 복구 연결, 평문 임시본 처리 기준 | B의 방식과 독립 복구 연결 | 보안 책임자 |
| 접근과 복구 권한 | 백업 기록자·검증자·복구자·삭제 권한, 비상 접근 가능 여부 | 운영/A 계정 사용 불가를 가정한 접근 검증 | 보안·복구 책임자 |
| 용량과 완결성 | 실제 크기, 증가분·첨부·복원 작업 공간 포함 가용 용량 | 전체 세트와 변경 이력 보존을 위한 용량 | 인프라 책임자 |
| 보존(retention) | 기존 승인 기간·버전·만료/자동 정리 동작, PG 보존과의 정합성 | B의 기간·만료/정리 동작 및 복구 의존성 유지 | 데이터·보안 책임자 |
| 운영 책임 | 수행자·검증자·장애 연락 담당과 대체자 | B 담당과 대체자, 정기 확인 책임 | 전환 책임자 |

모든 셀은 현재 미확인이다. 이 표는 새 보존 정책이나 특정 저장 상품 도입을 정하지 않는다. 기존 기준이 없거나 사용자 요구와 충돌하면 미결정으로 올리고 실제 실행을 보류한다. 만료 때문에 복구 키·원본·변경 이력이 먼저 사라지는 세트는 불합격이다.

## 5. A/B 각각의 독립 검증 절차

아래는 실제 데이터 접근·백업 범위와 실행 조건을 사용자가 명시한 뒤 별도 실행자가 수행한다. A 검증 결과를 B에 재사용하지 않는다.

1. **세트 고정:** 기준 시점/checkpoint, 포함 범위, schema·코드·codec 버전, 파일/객체 목록, 각 크기와 checksum, DB 모델/테이블별 object count, 첨부 총개수/bytes, 키 버전의 비공개 참조를 하나의 복구 세트 ID에 연결한다. manifest 자체의 무결성 근거는 기존 보안 보관 절차로 별도 보호한다.
2. **저장 후 재읽기:** A에서 실제 저장된 전 객체를 다시 읽어 파일 bytes checksum·크기·object count·누락/추가 객체를 원본 manifest와 비교한다. B도 자체 회수본으로 반복한다. 원본 업로드 전 hash나 A/B끼리의 일치만으로 완전성을 판단하지 않는다.
3. **복호화와 키 복구:** 운영 프로세스 메모리나 작업자의 기존 키 캐시를 쓰지 않고 승인된 복구 경로에서 필요한 활성·과거 키와 HMAC 키를 회수한다. 백업 매체와 필드 암호문을 검증·복호화하고 키 버전/AAD/HMAC 일치를 전수 검사한다. 키 누락·변조·오류는 실패로 남기며 평문 fallback/빈 값 대체를 금지한다.
4. **A 격리 복원:** 운영·원천·예약 작업·외부 전송 경로를 차단한 새 환경에 A만으로 PG 복구본, Mongo 이관본/복구본 및 파일을 복원한다. 이관 importer 성공과 실제 앱이 사용할 Mongo 구조 복구를 구분한다. 외부 첨부·필수 파일과 안전하게 분리된 키·설정도 복구한다.
5. **B 격리 복원:** A 복원 환경/로컬 캐시를 재사용하지 않는 새 환경에서 B만으로 같은 절차를 반복한다. 각각 schema/인덱스/validator/권한, row/object count, canonical 내용 digest, 참조·unique·HMAC, 첨부 bytes 및 연결을 대조한다. source에 이미 있던 이상도 누락 처리하지 않고 보존·판정한다.
6. **앱 검증:** 복원된 호환 버전으로 아래 업무표를 각각 수행한다. 허용된 격리 데이터 쓰기와 재시작 후 재조회도 포함한다. 오류·접근 거부·감사 기록을 확인하고 실제 외부 발송은 막는다.
7. **증거 확정:** A/B별 회수·복원 시작/완료 시각, 소요 시간, 실패·재시도, 집계 결과, 검증자와 증거 참조를 남긴다. 동일 checkpoint의 양쪽 복구가 통과해야 한다. 한쪽 실패, 오래된 세트, 범위 불명은 전체 전환 게이트 실패다.

암호화 nonce 때문에 서로 다른 export의 ciphertext digest는 같지 않을 수 있다. 동일 immutable spool과 대상은 정확한 ciphertext digest로 대조하고, 서로 다른 스냅샷/재암호화 결과는 승인된 격리 환경에서 ID·타입·정규화된 논리 값과 첨부 bytes를 비교한다. 복호화 값이나 행 단위 hash는 공개 증거에 남기지 않는다.

| 현재 기능 보존 검증 | A/B 각각의 합격 기준 |
| --- | --- |
| 로그인·역할·개인정보·코치 토큰 | 기존 허용/거부 사용자와 데이터 범위가 동일. 토큰·암호화·조회 감사 유지. 권한 확대나 우회 없음 |
| 운영 목록/상세·검색/정렬·편집·종료회고 | 기존 조회·필터·페이지·날짜/금액/null 의미 유지. 저장 후 재조회·재시작에도 동일 |
| 코치 일정/예약/투입/평가·콘텐츠·공지·첨부 | 충돌·중복·관계·삭제 상태 유지. 첨부 실제 다운로드 bytes·크기·권한 일치 |
| OM 요청/배정·명단·관리자·감사·리포팅 | 기존 트랜잭션·채번·집계·접근 거부·감사 유지. 누락된 요청이 PG로 쓰이지 않음 |
| 가져오기/staging/승격·Calendar·원천 연동·예약 작업 | 기존 사용 경로를 격리 adapter로 확인. 재시도·실패·멱등성·외부 처리 상태 보존. 실원천 변경·알림 발송 없음 |
| 백업·health·재기동 | 실제 선택한 Mongo backend 기준 상태 확인, 기존 백업 기능 계약 유지, 배포 시작 시 원치 않는 PG migration/쓰기 없음 |

이 표는 현재 사용 경로를 확정하기 위한 최소 인계 목록이다. 최신 기능 증거와 대조하여 실제 활성 CLI·예약 작업·페이지/API를 빠짐없이 연결해야 하며, 합성 성공을 실데이터 앱 검증으로 승격하지 않는다.

## 7. checkpoint·freeze·전환 순서

두 방식 중 **freeze 후 새 전체 스냅샷으로 최종 복사**를 우선 준비안으로 둔다. 기존 insert-only 도구와 맞고 삭제·중간 변경 누락을 줄이지만 중단 시간이 길어질 수 있다. **초기 복사 후 증분 동기화**는 중단을 줄일 수 있으나 누락 없는 변경/삭제 포착·순서·재시도·최종 비교가 추가로 검증되어야 한다. 현재 도구에는 이 기능이 없다. 실규모와 허용 중단 시간을 확인해 책임자가 확정하며, 시간을 맞추려고 데이터 일부를 제외하지 않는다.

checkpoint는 이름만으로 보장이 생기지 않는다. wall-clock 시각 외에 source snapshot, 검증 가능한 경계 식별자, 활성 writer 목록, 포함 파일 버전, 변경 이력의 시작/끝, 검증자 증거를 연결한다. 기존 도구의 snapshot ID를 영구 복원 지점이나 CDC cursor로 해석하지 않는다.

1. **C0 범위·책임 확정:** 9절 중 실제 접근·초기 백업의 선행조건을 먼저 닫고 사용자의 실제 접근·백업 대상 범위/조건을 기록한다. 이후 단계의 결정과 증거는 각 차단 시점까지 확보하며, 아직 수행하지 않은 Cfinal의 결과를 C0 선행조건으로 요구하지 않는다. 데이터·기술·보안·전환 책임자 검토를 받는다. 먼저 A/B 실제 백업과 각각의 복원 검증을 완료한다. 원본 PG와 키·파일을 보존한다.
2. **C1 초기 복사:** 승인된 일관 스냅샷에서 export하고 새 shadow namespace로 복사한다. snapshot·manifest·원천/대상 집계·관계·첨부·암호화 검증을 기록한다. 최초 복사는 최종 상태가 아니다. PG는 현재 서비스 기준으로 유지한다.
3. **Cf 쓰기 freeze:** 앱/API뿐 아니라 worker·예약·import·동기화·CLI·관리자 경로·재시도 큐 등 모든 writer를 중지한다. 진행 중 요청/트랜잭션을 종료·정산하고 미확정 결과를 분류한다. DB와 파일의 변화가 멈췄음을 증명한다. 외부 원천은 변경하지 않으며 유입 이벤트의 재처리 경계를 기록한다.
4. **Cfinal 최종 스냅샷·재대조:** freeze 상태에서 최종 전체 스냅샷을 새 run으로 확보하거나, 검증된 증분 경로로 C1 이후 생성·수정·삭제·관계 해제를 모두 반영한다. timestamp 필터만으로 삭제를 포착했다고 간주하지 않는다. 신규 전체 복사라면 C1과 Cfinal의 ID 집합/내용 차이를 조사해 삭제·추가·수정이 최종본에 정확히 반영됐음을 확인한다. 물리 삭제가 발견되면 원본 보존본과 근거를 유지하고 임의로 재삭제하지 않는다.
5. **최종 일치 판정:** Cfinal PG와 Mongo의 ID 집합·건수·논리 값·관계·감사·삭제 상태·외부 처리 연결·파일을 재대조한다. sequence 값/호출 여부/증분과 업무상 최대 식별자, Mongo 다음 채번의 충돌 여부를 확인한다. 최종 스냅샷/필수 로그·파일을 포함하는 동일 Cfinal 복구 세트를 A/B에 확보하고 **각각 checksum·count·키 복구·격리 복원·앱 검증을 다시 통과**시킨다. 초기 C1 복원 결과로 대체하지 않는다. 이 시간도 freeze 예산에 포함한다.
6. **Cswitch 읽기 연결 확인:** 검증된 운영용 Mongo 구조에 앱 전체를 연결하는 승인된 절차를 적용한다. 아직 일반 쓰기는 열지 않는다. health·권한·기존 화면·첨부·PG fallback 없음·실행 버전을 확인한다. 원본 PG는 보존하며 양쪽 writer를 동시에 열지 않는다.
7. **Cwrite 쓰기 개시:** 전환 후 Mongo 쓰기와 파일 변화의 복구 경로가 검증되었을 때만 재개한다. 첫 성공 쓰기 경계, 이후의 연속된 변경/삭제 및 외부 처리 상태를 보존한다. 시험 쓰기도 실제 Mongo 쓰기로 계산한다. 오류/감사/건수/동기화 상태를 관찰하고 8절의 조건에 따라 즉시 중단한다.
8. **Caccept 인수:** 정해진 관찰 기간·복구 지표·업무 검증과 Mongo 백업 A/B 복원 증거를 책임자가 확인한다. 이 문서의 인수는 원본 PG·백업·키·파일 삭제 승인이 아니다. 보존 만료 처리도 별도 기존 절차에 따른다.

## 8. 중단·복귀 조건과 전환 후 쓰기 보존

| 상황 | 즉시 조치 | 재개/복귀 조건 |
| --- | --- | --- |
| A/B 중 하나 누락·손상·키/권한·용량 실패, 범위 불명 | 다음 단계 중단. 원본/실패 세트/로그 보존 | 실패 원인 해결 후 해당 세트와 양쪽 동일 checkpoint 완결성을 다시 검증 |
| count/digest/첨부/관계 불일치, 암호화·권한 회귀 | 쓰기 재개 금지. mismatch를 빈 값/누락으로 숨기지 않음 | 모든 불일치 판정 및 재검증. 유실 허용 예외를 만들지 않음 |
| freeze 중 writer 재유입 또는 checkpoint 불명 | Cfinal 무효 처리, 전환 중단 | writer 원인 차단 후 새 checkpoint·새 세트로 최종 검증 반복 |
| Mongo 쓰기 개시 전 연결/앱 검증 실패 | Mongo 쓰기 없음의 증거 확인 | PG가 최신이며 변경되지 않았음을 확인한 후 승인된 PG 앱/구성으로 재개. Mongo에 시험 쓰기라도 있거나 결과가 불명확하면 아래 경로 적용 |
| Mongo 쓰기 개시 후 장애 | 양쪽 업무 writer·외부 부작용 중지. PG로 주소만 돌리지 않음 | 최신 쓰기까지 보존하는 전진 복구 또는 검증된 역이관 완료 후 한쪽만 재개 |
| 허용 중단 시간 초과 | 유실/미검증을 감수하고 강행하지 않음 | 쓰기 전이면 위 PG 복귀, 쓰기 후이면 아래 복구. 시간 연장/재시도는 책임자가 결정 |

### Mongo 쓰기 이후의 복구 절차

1. 장애 경계 **Cr**을 고정하고, 성공 응답한 쓰기뿐 아니라 timeout/재시도 등 결과 불명확한 요청도 확인한다. Cwrite 이후 DB 생성·수정·삭제 상태, 파일 버전/bytes, 감사·채번·토큰·외부 이벤트 연결을 유실 없이 확보한다. 일부 감사 로그만으로 전체 변경 재현이 가능하다고 가정하지 않는다.
2. 현재 Mongo 상태와 변경 이력, 첨부/필수 파일을 보존하고 A/B의 마지막 검증 세트 및 후속 이력과 연결한다. 기존 데이터를 덮어써 복구 근거를 없애지 않는다. 장애 Mongo에 접근할 수 없다면 마지막 성공 쓰기까지 복구 가능한 증거가 확보될 때까지 서비스 쓰기를 중단한다.
3. **전진 복구:** 검증된 백업+연속 변경 이력 또는 손실 없는 현재 상태를 새 격리 Mongo에 복원하고 Cr까지 재현한다. PG 역변환 위험은 적지만 Mongo 장애 원인과 최신 이력 접근이 해결되어야 한다. 앱 호환성과 DB/파일·권한·암호화·감사·채번·외부 처리 상태를 검증한 뒤 승인된 환경을 승격한다.
4. **PG 역이관:** 이 경로가 필요하면 원본 PG를 직접 덮어쓰지 않고 보존본에서 별도 PG 후보를 만든다. Cwrite~Cr의 생성·변경·삭제/관계 해제·첨부 변화를 멱등적으로 반영한다. ID/Decimal/날짜/null·암호문/AAD/HMAC·현재 권한을 보존하고 PG schema·제약·채번 및 호환 앱을 검증한다. 외부 발송/Calendar 등의 이미 처리된 효과를 중복 실행하지 않게 처리 상태도 복원한다. 전체 현재 Mongo 논리 상태와 대조한 후에만 PG 후보로 복귀한다.
5. 선택된 후보를 A/B 복구 세트 및 checkpoint와 연결하고 격리 앱 검증·재시도 검증을 통과한 뒤 책임자가 단일 writer 재개를 결정한다. 최신 쓰기 보존이 증명되지 않으면 **중단 유지**가 기본이다.

전진 복구와 PG 역이관 중 실제 운영 가능한 주 경로와 대체 경로를 쓰기 개시 전에 확정해야 한다. 현재 읽은 export/import에는 운영 역이관 구현이 없으며, Mongo 최신 쓰기 복구 수단도 이 문서에서 검증하지 않았다. 무손실 요구는 두 개의 오래된 백업만으로 보장되지 않는다. 첫 Mongo 쓰기부터 장애 경계까지 복구 가능한 지속성·기록·파일 보존 범위와 실패 조건을 검증하지 못하면 Cwrite를 열지 않는다.

## 10. 증거 장부와 다음 실행자 인계

실제 장부는 승인된 비공개 보관처에서 관리한다. 공개 문서에는 익명 증거 ID·집계 판정만 남긴다. 실제 위치·원천 파일명·고객 정보·키·접속값·행 단위 hash를 쓰지 않는다.

| 장부 필드 | 기록 기준 |
| --- | --- |
| 실행 ID·범위·승인 | 사용자 범위/조건 확인 참조, 수행자·검증자·전환 결정자, 시작/완료 시각 |
| 버전·시점 | 코드/schema/codec/암호화 정책 버전, 세트 ID, C0/C1/Cf/Cfinal/Cswitch/Cwrite/Cr 연결 |
| 원천/대상 대조 | 모델/객체 목록, row/object count, 첨부 count/bytes, 내용 digest·파일 checksum 판정, 불일치/제외/오류 판정 |
| A 증거 | 실제 저장 후 재읽기·키 복구·격리 PG/Mongo/파일 복원·앱 검증의 개별 증거 ID와 결과 |
| B 증거 | A와 독립된 동일 항목의 증거 ID와 결과, A/운영 호스트 의존 여부 |
| freeze·최종 차이 | writer 중단/종료 증거, 변경/삭제·sequence·파일 경계 대조, 최종 세트 A/B 재검증 |
| 쓰기 후 복구 | 마지막 확인 쓰기/불명확 요청 판정, 변경 이력 연속성, Cr까지 복원·역이관 결과, 단일 writer 재개 승인 |
| 실패·잔여 | 오류 코드, 영향 범위, 실패 세트 보존 참조, 재시도 경계, 미검증·D01~D12 상태 |

현재 장부 상태: 실제 백업 A 미확인 / B 미확인, checksum·object count 미검증, 키 복구 미검증, 격리 복원 미실행, 실데이터 앱 검증 미실행, 최종 변경/삭제·freeze 미실행, 전환/rollback 미실행. 모두 성공으로 표시할 수 없다.

다음 실행자는 우선 D01~D06의 범위·책임·보안 보관과 기존 수단을 확정하고, 최신 구현 증거로 6절의 준비 작업을 배정한다. 이후 합성 리허설과 실제 A/B 복원 증거를 구분해 확보한 뒤 Cfinal/Cwrite의 게이트를 판정한다. 운영 실행 명령·저장 위치·비밀 주입값은 승인된 별도 비공개 절차에서만 확정한다.

이번 문서 작업에는 migration, 운영 DB write, 원천 import/write-back, 배포/권한/설정 변경, 새 의존성 추가가 없다. 코드와 문서의 정적 검토는 운영 복원 가능성 검증을 대신하지 않는다.
