# 가져오기 운영 반영의 Mongo 경계

2026-09-30, 기준 `75125c9`. 구현·합성 검증·독립 코드 수락을 마쳤다. 최종 정리·원격 통합 여부는 `.claude/plans/mongodb-import-promotion/` 기록을 따른다.

## 저장 경계와 기존 동작

가져오기 반영 POST는 명시 `importPromotion`, `teamMembers`, `importPromotionCalendar`, 기존 `requestActivity`를 사용한다. 저장소가 빠지면 업무 시작 전에 거부하며 PostgreSQL이나 실제 Calendar로 대신 연결하지 않는다. 명시 context 밖의 기본 저장소는 PostgreSQL이고, 기존 workspace 권한을 유지한다.

임시 저장된 미연결 행 전체를 검토한다. 화면의 200건 표시 제한은 반영 제한이 아니다. 검증 오류·OM·LD·기업·과정·날짜 순서로 차단 사유를 결정한다. Notion 검수 자료는 기존대로 반영을 막는다. 원천 지문 일치, 활성 업무키 일치, 기업/과정 갱신 또는 생성, 신규 운영 생성 순서를 유지한다. 삭제 표시된 지문 일치는 기존 운영의 값을 복원하며 식별자와 과정 연결은 바꾸지 않는다. 실패 행은 지우지 않는다.

Mongo의 기업·과정·운영·원천 연결과 변경 감사는 한 transaction이다. source 모델에 새 변경 감사를 추가하지 않는다. 승인된 결과의 차단 사유와 복호화 표시를 저장 데이터·로그의 평문 노출과 구분한다. 비정형 오류는 고정 문구로 응답한다.

부모 가져오기 이력 없이 source만 남은 손상 상태는 전부 차단 행이어도 거부한다. 없는 이력과 source가 모두 없는 요청은 기존 빈 결과를 유지한다. 필수 기업·과정 참조가 깨진 경우도 부분 반영 없이 거부한다.

원본과의 교차 검증에서 일반 Mongo 등록의 생성 감사에 빈 값 필드가 빠지는 문제도 발견했다. Company/Course/OperationSession의 실제 생성에 한해 PG와 같은 필드 집합을 기록하도록 보완했다. 수정·동일 값 재실행의 감사 생략과 개인정보 가림은 유지한다.

## 동시 실행과 재시도

기존 과정명 복원 guard를 predicate 조회 전에 사용한다. promotion끼리와 과정명 복원·OM 배정은 이 guard를 공유하지만 일반 운영 등록·삭제까지 잠그는 것은 아니다. Mongo 문서 쓰기 충돌은 기존 알고리즘 전체를 새 snapshot에서 실행한다. 정확한 Company/Course 자연키 insert 경합도 같은 방식으로 최대 다섯 번 시도한다. ID·지문·순번 unique, 감사 실패, commit 불확실성을 무조건 재시도하는 규칙은 아니다.

같은 업무키의 일반 등록이 겹치면 PG의 특정 실행 순서는 두 운영을 만들고 Mongo 재조회는 기존 운영에 연결할 수 있다. 원본 PG의 허용 직렬 결과와 대조하며 이 동시 실행 차이를 감추지 않는다. 일반 등록은 같은 업무키를 여러 번 만들 수 있으므로 전역 중복 방지나 항상 한 건이라는 보장이 아니다. 상세 실행 근거는 별도 검증 기록에 남긴다.

이미 반영된 행은 재실행에서 제외되지만 차단 행은 미연결로 남아 같은 사유로 다시 집계된다. PG sequence는 실패나 upsert에서도 번호를 소비할 수 있고 Mongo 내부 counter는 transaction과 함께 rollback된다. 번호열 자체의 일치 대신 고유성·기존 최대값·고갈·공유 writer 경합을 검증한다.

## 저장 이후 Calendar와 실패 판정

Calendar는 업무 commit이 확인된 뒤 요청당 한 번 호출한다. transaction callback이나 commit 응답 재시도 중에는 호출하지 않는다. 결과가 빈 요청이나 사용자가 다시 보낸 요청도 각각 한 번 호출한다. 따라서 전역 단 한 번 실행을 보장하는 계약은 아니다.

- commit 전 확정 실패: 업무·변경 감사·내부 counter가 모두 취소된다.
- commit 결과 불명: 전체 반영됐거나 전혀 반영되지 않았을 수 있다. 실패 응답만으로 삭제·복구하지 않는다.
- Calendar 실패: 반영 내용은 유지하고 성공 응답에서 Calendar 결과를 생략한다. 로그는 고정 문구다.
- 페이지 갱신 실패: 원본처럼 오류 응답이지만 이미 저장된 내용과 Calendar 실행은 유지된다. 오류 응답을 미반영 증거로 삼지 않는다.
- 별도 요청 감사 실패: 기존 응답과 업무 commit을 취소하지 않는다.

실제 Google 연결·저장·잠금 전환은 후속 Calendar 단위다. 이번 검증은 실제 API와 로컬 MongoDB에 합성 Calendar 효과를 연결한다.

## 한계와 운영 적용

Mongo 업무 전체 예산은 명단 조회 전부터 60초이며 재시도로 초기화하지 않는다. 명단 조회를 강제 취소하거나 Calendar까지 포함한 전체 응답 시간을 보장하는 것은 아니다. scan별 15초·20,000행·32MiB 제한을 초과하면 부분 성공을 반환하지 않는다.

shadow 준비는 명시 validator/index와 shared counter high-water를 확인한다. runtime open은 준비되지 않은 저장소를 수리하지 않는다. 기존 namespace를 자동 삭제하거나 기존 데이터를 무조건 변환하지 않는다.

기본 PG, 생산 설정, 운영 데이터는 변경하지 않는다. 전체 앱 연결, Sheets/Notion·Drive의 나머지 경계, 실제 A/B 백업·복원·데이터 복사·최종 전환은 별도 미완료다. 이 기능 구현만으로 dev→main이나 운영 이전 완료를 판단하지 않는다.
