# 공지·첨부 저장 경계

공지 목록·상세·작성·수정·삭제·첨부 다운로드와 목록/상세/수정 페이지를 `AnnouncementRepository`로 연결한다. 명시 내부 `announcements` context에서만 Mongo를 주입하며 기본 PostgreSQL을 유지한다. 요청으로 backend나 권한을 선택하지 않는다.

관리자 확인, 기존 HTML 정제·제목/본문 검사, API 응답, 다운로드 헤더와 UI를 유지한다. 공지는 소프트 삭제하며 첨부 문서를 보존한다. 공지 수정에서 선택한 첨부만 해당 부모 안에서 물리 제거한다. 새 삭제 정책이나 영구삭제 API는 추가하지 않는다.

## 암호화·첨부·감사

기존 35모델 정책으로 제목·본문·작성자·삭제자·파일명·첨부 bytes를 암호화한다. 승인된 화면과 다운로드의 복호화 값은 저장 평문과 구분한다. 전체 행을 인증한 후 필요한 응답 필드만 선택한다. 파일당5MiB·최대5개의 정상 요청을 암호화 후에도 저장·조회·다운로드할 수 있도록 첨부는 부모와 분리된 기존 모델을 유지한다.

첨부의 BSON 크기로 짧은 응답 묶음이 생겨도 마지막 실제 ID 다음부터 계속 읽는다. 첨부 메타데이터 조회는 단건 인증 후 bytes를 결과에 보관하지 않는다. 첨부 전용64MiB/20k행/15초 예산을 적용하며 공통32MiB scan 한도는 바꾸지 않는다. 한도 초과는 일부 결과를 성공으로 반환하지 않는다. 전체 transaction 재시도 예산은30초다. 이 안전한도는 기존 PG에 없는 Mongo 병렬 검증 제약이며 운영 성능 보장을 뜻하지 않는다.

부모 변경·첨부 생성/삭제·ActivityChange는 한 transaction에서 처리한다. 기존 작성자/등록시각과 남긴 첨부 ciphertext는 유지한다. 첨부 감사 공개값은 기존 PG trigger와 같이 announcement_id/mime_type/size뿐이고 파일명·bytes는 가린다. 큰 Bytes를 감사 비교용으로 바이트별 객체/JSON으로 펼치지 않는다. 요청 감사의 후행 실패는 이미 성공한 업무를 되돌리지 않는다.

## 이번 범위에서 유지한 기존 한계

PUT은 먼저 존재/삭제 여부와 첨부 수를 읽고, 입력 검증 후 별도 쓰기를 실행한다. 제거 ID 개수를 단순히 빼는 기존 계산에는 중복·다른 공지·없는 첨부 ID도 포함된다. 따라서 동시 추가나 잘못된 제거 목록으로 실제 첨부 수가5를 넘을 수 있다. 이 전환에서 새 상한 정책이나 원자적 개수 재검사를 혼입하지 않았다. 실제 삭제는 해당 부모의 일치하는 첨부에만 적용한다.

사전 조회 뒤 다른 요청이 공지를 삭제하면 이미 검증된 PUT이 내용을 바꿀 수 있지만 삭제 상태를 되돌리지는 않는다. Mongo도 이 계약을 보존한다. 이후 상세/편집/다운로드는404이고 목록에서 제외된다. 첨부 추가 PUT 재실행은 새 첨부를 만들 수 있으며 새 멱등성 정책을 추가하지 않는다.

한 Mongo 메서드의 부모/관계 조회는 snapshot이다. 원본 PG의 별도 사전 조회·쓰기와 요청 전체를 같은 snapshot으로 묶는 것은 아니다. UUID 허용 표기·부재/무효 오류와 감사 세부값은 실제 합성 PG 원본 oracle과 비교한다.

## 검증·남은 작업

실행 결과와 실패 보완·독립 수락·정리·통합 SHA는 `.claude/plans/mongodb-announcements/`를 따른다. 일반 최종 898pass/48skip, 실제 PG 대조 6pass, native 30pass, 실제 handler/page 13pass, typecheck/build 및 lint 0error/기존7warning을 확인했다. 묶음은 겹치므로 합산하지 않는다. 전체 Mongo 회귀·최종 독립 수락과 원격 통합은 해당 기록을 따른다. 실제 OAuth/브라우저 E2E·운영 부하·실데이터 복사·복원 리허설·최종 운영 전환은 별도 미완료다. 운영/실원천/실키·env/배포는 변경하지 않는다.

서비스 이전까지 남은 기능·앱 전체 연결·실제 데이터 작업은 [잔여 순서](mongodb-cutover-remaining.md)를 따른다.
