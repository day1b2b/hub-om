# MongoDB 전환 운영 장애 회고

## 결론

이번 장애의 직접 원인은 운영 애플리케이션의 여러 읽기·쓰기 경로를 한 번에 MongoDB로 전환했지만, 실제 운영 런타임에서 MongoDB 연결과 각 repository 전환 경로가 모두 동작한다는 증거가 없는 상태로 배포한 것입니다. 자동 테스트는 개별 코드와 합성 데이터의 동작을 확인했지만, 운영 네트워크·계정·환경변수·실제 요청 흐름을 포함한 검증을 대신하지 못했습니다.

문제는 특정 함수 하나가 아니라 전환 방식과 배포 통제의 결함이었습니다. 일부 증상만 고치는 핫픽스로는 다른 경로의 동일한 실패를 막을 수 없었고, 최종적으로 전환 전 PostgreSQL 버전 전체를 복구해 정상화했습니다.

## 확인된 사실

- MongoDB 전환 PR #638 배포 직후 서비스 503과 업무 기능 장애가 발생했습니다.
- 운영 로그에서 일정·시간 저장 실패는 `OPERATION_WRITE_COMPOSITION_FAILED`의 연결 단계 실패로 확인됐습니다.
- 업무요청 저장 후 Slack 알림 누락, OM 배정 실패, 운영 일정·시간 저장 실패처럼 서로 다른 기능에서 장애가 나타났습니다.
- PR #641은 일부 경로를 보완했지만 모든 MongoDB 선택 경로를 정상화하지 못했습니다.
- 전환 전 커밋으로 운영 이미지를 되돌리자 PostgreSQL health check, 주요 화면, 일정·시간 저장이 정상화됐습니다.
- 이후 PR #642와 #643으로 `dev`와 `main`도 같은 PostgreSQL 코드 트리로 영구 복구했습니다.

## 원인

### 직접 원인

운영 환경의 여러 `*_BACKEND` 선택값이 MongoDB 경로를 가리키는 상태에서 애플리케이션이 MongoDB 연결을 완성하지 못했습니다. 연결 실패가 발생한 쓰기 경로는 PostgreSQL로 자동 복귀하지 않았기 때문에 요청이 실패했습니다.

### 구조적 원인

1. **전환 범위가 너무 컸습니다.** 읽기, 쓰기, 관리자, 업무요청, 알림 관련 경로를 한 배포에서 함께 바꿔 실패 범위가 넓어졌습니다.
2. **운영과 같은 조건의 사전 검증이 부족했습니다.** 합성 검증과 코드 테스트는 통과했지만, 운영 컨테이너에서 실제 선택값으로 연결·조회·쓰기 준비 상태를 확인하는 단계가 없었습니다.
3. **health check가 핵심 업무 흐름을 대표하지 못했습니다.** 프로세스 기동 또는 단일 DB 확인만으로는 일정 저장, OM 배정, 알림 큐잉 같은 경로의 실패를 발견할 수 없었습니다.
4. **소프트 실패가 관측되지 않았습니다.** Slack 알림 예외가 요청 성공과 분리되어 있었고 에러 객체가 기록되지 않아 저장 성공 뒤 알림 실패를 즉시 진단하기 어려웠습니다.
5. **부분 핫픽스의 안전 범위를 과대평가했습니다.** 한두 composition을 수정한 뒤 동일 선택 구조를 쓰는 나머지 경로를 전수 확인하지 못했습니다.
6. **코드와 운영 설정의 변경 통제가 분리돼 있었습니다.** PR 검증이 통과해도 Coolify의 실제 backend selector 조합이 안전한지는 자동으로 차단되지 않았습니다.
7. **롤백을 즉시 영구화하지 않았습니다.** 런타임 이미지만 먼저 롤백하면 다음 자동 배포에서 문제가 재발할 수 있었습니다.

## 잘된 대응

- 운영 PostgreSQL 데이터와 스키마를 변경하지 않아 원본이 보존됐습니다.
- 전환 전 이미지를 이용한 롤백이 가능했고 서비스가 빠르게 정상화됐습니다.
- 복구 뒤 동일한 Git tree를 `dev`와 `main`에 반영해 다음 배포의 재발 가능성을 제거했습니다.
- 실제 일정·시간 저장 경로와 health check, 주요 화면, 전체 자동 검증을 함께 확인했습니다.

## 부족했던 대응

- 첫 장애 뒤 전체 selector 목록을 즉시 PostgreSQL로 되돌리지 않고 부분 수정부터 시도했습니다.
- 사용자 영향이 확인된 시점에 전환 작업을 자동 중단하는 명확한 기준이 없었습니다.
- 실제 Slack 발송처럼 외부 영향을 만드는 검증과, 외부 영향 없이 실행할 수 있는 알림 준비 상태 검증이 분리돼 있지 않았습니다.
- 대규모 원복 PR에서 커스텀 보안 점검이 운영체제 인자 길이 제한으로 실행되지 않았습니다.

## 재발 방지 원칙

### 배포 전

- DB 또는 repository 선택 경로 변경 PR에는 `database-change-reviewed` 라벨과 데이터/기술 책임자 검토가 필요합니다.
- 실제 운영 selector를 바꾸는 PR에는 추가로 `database-cutover-approved` 라벨이 필요합니다.
- 전환은 한 번에 한 기능군만 진행합니다. 읽기 전환과 쓰기 전환을 같은 배포에서 하지 않습니다.
- 쓰기 전환 전 운영과 같은 네트워크 경계에서 연결, 권한, index, sequence, 암호화 키, 읽기·쓰기 준비 상태를 확인합니다.
- PostgreSQL 경로와 복귀 절차를 유지한 상태에서만 전환합니다.
- 배포할 커밋 SHA, 되돌릴 이미지 SHA, selector 변경 전후 값을 비밀 없이 변경 기록에 남깁니다.

### 배포 중

- 첫 단계는 읽기 전용 shadow 또는 내부 사용자 범위로 제한합니다.
- 핵심 기능을 순서대로 확인합니다: health, 로그인, 대시보드, 운영 조회, 일정 저장, OM 배정, 업무요청 저장, 알림 준비 상태.
- 사용자 오류율, DB 연결 오류, composition 실패가 한 건이라도 새로 나타나면 다음 단계로 진행하지 않고 즉시 직전 버전으로 복구합니다.
- 쓰기 selector는 한 배포에 하나만 전환합니다.

### 배포 후

- 최소 30분 동안 새 연결 오류와 업무 요청 실패를 관찰합니다.
- 런타임 롤백을 했다면 같은 작업에서 `dev`와 `main`도 정상 트리로 복구합니다.
- 알림은 실제 채널 발송과 준비 상태 검증을 분리하고, 준비 실패에는 원인을 식별할 수 있는 구조화 로그를 남깁니다. 개인정보와 비밀은 기록하지 않습니다.

## 다음 MongoDB 이전의 재개 조건

실행 순서와 완료 증거는 [MongoDB 전환 TODO](mongodb-cutover-todo.md)에 기록합니다.

아래 항목이 모두 충족되기 전에는 MongoDB selector를 운영에서 사용하지 않습니다.

- [ ] 기능군별 전환 목록과 순서 확정
- [ ] 운영 컨테이너에서 읽기 전용 연결 검증
- [ ] 각 repository의 PostgreSQL/MongoDB 계약 테스트
- [ ] 실제 selector 조합을 사용하는 배포 전 smoke test
- [ ] 일정 저장·OM 배정·업무요청·알림 준비 상태 검증
- [ ] 자동 rollback 기준과 직전 이미지 확인
- [ ] A/B 백업 및 각 격리 복원 검증
- [ ] 데이터/기술 책임자 승인 라벨 확인
- [ ] 운영 담당자에게 영향 시간과 복구 기준 공유

## 확신도와 한계

원인 판단의 확신도는 **높음**입니다. MongoDB 전환 직후 여러 repository 경로에서 연결 실패가 발생했고 동일 코드 전체를 PostgreSQL 버전으로 복구한 뒤 정상화됐기 때문입니다. 다만 최초 연결 실패의 세부 원인이 네트워크, 자격 증명, 드라이버 설정 중 어느 하나였는지는 당시 로그가 충분하지 않아 확정하지 않습니다. 재발 방지는 특정 연결 원인 하나보다 전환 범위, 관측성, 검증, 롤백 통제를 함께 강화하는 방식으로 설계합니다.
