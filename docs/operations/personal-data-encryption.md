# 개인정보 저장 암호화

## 범위와 계약

`src/lib/privacy/fields.json`이 서버 저장 암호화 대상(25개 테이블, 125개 필드)의 단일 목록이다. `inventory.json`은 나머지 업무 필드까지 분류하며 테스트가 미분류 신규 필드를 차단한다.

- 담당자·코치·강사·직원 이름/정규화 이름, 이메일, 전화번호, 생년월일, 사번, 개인 외부 식별자, Slack ID, 코치 접근 토큰.
- 담당/작성/수정/삭제/예약/조회 주체, 개인 캘린더/문서 링크, 자유 입력 메모·강의관리·피드백·공지와 첨부파일.
- 원천 행, 미매핑 필드, 검증 로그, 동기화 상세, Notion 프로필, coach-db 보관본 등 JSON 전체.
- 활동 로그 작성자와 기존 변경 내역. 새 DB 트리거의 변경 내역에는 개인정보 값을 넣지 않고 변경 표시만 남긴다.
- 서버의 로컬 JSON 대체 저장소(운영현황, 직원 명단, OM 요청, 강사 위키, 리마인더 발송 이력)는 파일 전체를 암호화한다.

관계 유지용 내부 UUID/FK, 숫자형 Notion 연결 번호, 업무 날짜·시간·상태·분류·집계 수치, 기업/과정 식별자는 업무 조회에 필요한 구조 정보로 유지한다. 이들은 연결된 자료와 함께 해석하면 개인정보가 될 수 있으므로 접근 통제 대상이다. 이번 구현은 DB/서버 저장 암호화이며, 권한 있는 화면·다운로드·외부 Google/Slack 원천에는 원래 정보가 보인다. 브라우저의 기존 강의관리 초안(localStorage), 과거 DB 백업·WAL·외부 원천 파일은 이 마이그레이션으로 암호화되지 않는다. 브라우저 초안까지 포함한 단말 저장 보호는 별도 전환이 필요하다.

## 방식과 기능 영향

Node.js `crypto`의 AES-256-GCM, 매 저장마다 무작위 12바이트 nonce, 16바이트 인증 태그를 사용한다. 모델·필드·키 버전을 AAD로 묶어 변조/다른 필드로의 복사를 거부한다. 키 누락·복호화 실패는 평문으로 대체하지 않는다. 키는 DB와 별도 서버 secret에 둔다. [Node.js 공식 crypto 문서](https://nodejs.org/api/crypto.html).

복원 불가능한 해시만 쓰면 이름 등을 표시할 수 없어 채택하지 않았다. 검색은 암호문과 독립적인 HMAC-SHA256 키로 만든 blind index를 사용한다. 이는 같은 필드의 동일 값 여부와 빈도는 드러낸다. `PiiIndex`와 `Encrypted` 보조 필드는 API 결과에서 제거한다. 생년월일/복귀일의 원래 날짜 컬럼은 NULL로 비우고 별도 암호문에 저장하며 앱에는 Date로 복원한다.

부분 문자열/대소문자 무시 검색과 이름 정렬은 서버에서 복호화 후 처리한다. 대상 테이블 최대 20,000행을 넘으면 결과를 잘라 반환하지 않고 오류를 낸다. 대규모 조회에는 정확한 값 검색이 필요하다. 암호화된 필드에 대한 SQL 집계·커서 정렬 등 지원하지 않는 조건은 명시적으로 거부한다. 활동 인원수 집계는 검색 해시로 묶는다.

직접 `pg` SQL을 사용하는 기존 CLI import/export/backfill은 새 컬럼을 감지하면 실행을 거부한다. 앱의 Prisma repository와 동기화 API는 암호화를 사용한다. CLI를 다시 활성화하려면 해당 작업을 공통 암호화 repository로 옮겨 검증해야 한다. 소스 DB·SQL을 우회해 평문을 적재하지 않는다. 신규 CLI도 같은 제한을 지킨다.

## 운영 반영 절차

**서비스 중지 및 백업 확인이 필요한 변경이다.** 앱만 먼저 배포하거나 백필 도중 트래픽을 재개하면 검색 해시가 비어 있는 데이터가 조회되지 않을 수 있다. `db-write-safety.md`에 따라 사용자에게 백업 확인과 실행 범위를 받은 후 진행한다.

1. DB 백업/복원 가능 여부를 확인하고 앱·스케줄러·적재 작업을 중지한다. 비공개 보관본도 접근 권한과 암호화를 확인한다.
2. 서로 다른 난수 32바이트 키 두 개를 보안 저장소에서 생성한다. `PII_ENCRYPTION_KEYS`(키 ID → base64 JSON), `PII_ACTIVE_KEY_ID`, `PII_INDEX_KEY`를 서버 secret으로 설정한다. 저장소/로그/명령 인자에 키를 남기지 않는다. `.env.example`에는 형식만 있다.
3. 테스트 DB에서 검증한 `20260909150000_pii_encryption` migration을 반영한다. 과거 migration 파일은 수정하지 않는다.
4. `npm run privacy:migrate`로 읽기 전용 점검을 실행한다. 행수·암호화/평문 필드 수·검색 해시 불일치 수만 출력한다.
5. 백업과 서비스 중지를 확인한 후 `npm run privacy:migrate -- --apply --backup-confirmed --maintenance-confirmed`를 실행한다. 200행씩 잠금/트랜잭션 처리하며 정상 암호문을 검증 후 건너뛰어 중단 후 재실행할 수 있다. 잘못된 키/손상 값은 즉시 중단한다.
6. `npm run privacy:migrate -- --enforce --backup-confirmed --maintenance-confirmed`로 전수 복호화 검증과 평문 저장 거부 제약을 설치한다. 모든 테이블의 plaintext/invalidIndexes가 0이어야 한다. 이후 직접 SQL의 평문 쓰기도 거부된다.
7. 로컬 저장소 사용 시 `npm run privacy:migrate-file -- --file=/비공개/경로 --purpose=operations`로 점검한 뒤 `--apply --backup-confirmed`를 추가해 원자적으로 교체한다. purpose는 `operations`, `team-users`, `om-requests`, `instructor-wiki`, `reminder-sent` 중 하나다. 기존 파일을 버리거나 빈 데이터로 대체하지 않는다.
8. `PII_ALLOW_PLAINTEXT_READS=false`로 유지하고 새 앱을 시작한다. 이름 검색·정렬, 코치 토큰 인증, 개인정보 상세, 첨부 다운로드, 활동 로그를 확인한다.

`PII_ALLOW_PLAINTEXT_READS=true`는 격리된 점검 용도다. 쓰기는 항상 암호화한다. 혼합 데이터 상태에서 일반 서비스 운영을 허용하는 옵션이 아니다.

## 키 교체와 복구

새 키 ID를 키 목록에 추가하고 활성 ID를 바꾸면 새 저장은 새 키를 쓴다. 기존 암호문에 필요한 이전 키는 계속 보관한다. 현재 백필 도구는 정상 암호문을 그대로 유지하므로 기존 암호문 전체의 키 교체 도구로 쓰지 않는다. `PII_INDEX_KEY`를 바꾸면 검색/중복 방지가 깨지므로 별도 점검·전체 인덱스 재생성 계획 없이 바꾸지 않는다.

코드만 이전 버전으로 되돌리면 암호문을 읽게 된다. 실패 시 서비스를 중지한 상태에서 암호화 호환 코드를 수정하거나, 승인된 변경 전 백업과 해당 코드 버전을 함께 복원한다. 부분 백필은 같은 키로 재실행할 수 있다. 키를 잃으면 암호문에서 원문을 복구할 수 없다.

## 검증

단위 테스트는 암복호화·변조·잘못된 키/필드·키 교체·필드 분류를 확인한다. `database.integration.test.ts`는 전용 로컬 PostgreSQL `127.0.0.1:55439/pii_test`에서만 실행되며 운영 연결을 거부한다. 기존 스키마를 빈 DB에 생성한 뒤 새 migration을 적용하고 `PII_TEST_DATABASE_URL`을 지정한다. 테스트 DB는 매 실행마다 새로 준비한다. 실제 운영 DB에는 테스트를 실행하지 않는다.
