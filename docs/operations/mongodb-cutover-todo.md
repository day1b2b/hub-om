# MongoDB 전환 TODO

이 문서는 2026-10-06 전환 장애 이후 MongoDB 이전을 안전하게 재개하기 위한 실행 목록입니다. 체크 표시에는 추정이나 구두 확인을 사용하지 않습니다. 각 항목의 **완료 증거**를 남긴 경우에만 완료로 처리합니다.

현재 운영 기준은 PostgreSQL입니다. 1~4단계가 모두 끝나기 전에는 운영 selector, 환경변수, 배포 이미지를 변경하지 않습니다.

## 완료 판정

- **담당**: `작업자`는 기술 작업을 수행하는 사람, `책임자`는 최종 전환을 승인하는 사람입니다.
- **완료 증거**: 성공 여부, 실행 시각, 대상 커밋, 비밀을 제거한 결과 또는 로그 위치를 기록합니다.
- **중단 조건**: 연결 오류, composition 오류, 데이터 불일치, 권한 오류, 기존 기능 실패가 하나라도 발생하면 다음 단계로 진행하지 않습니다.
- **복구 우선**: 운영 영향이 발생하면 원인 분석보다 PostgreSQL 정상 상태 복구를 먼저 수행합니다.

## 1. 운영 영향 없는 사전 확인

- [ ] **작업자**: 운영 서비스가 PostgreSQL을 사용 중인지 확인합니다.
  - 완료 증거: health 정상, 주요 화면 정상, PostgreSQL selector 목록 기록
- [ ] **작업자**: 운영과 같은 네트워크 경계에서 MongoDB 읽기 전용 연결을 확인합니다.
  - 완료 증거: 연결·인증·대상 DB 확인 성공, 비밀을 제외한 결과 기록
- [ ] **작업자**: MongoDB 인덱스, validator, sequence 준비 상태를 다시 확인합니다.
  - 완료 증거: 기대 목록과 실제 목록의 불일치 0건
- [ ] **작업자**: 개인정보 암호화 키를 출력하지 않고 암호화·복호화 왕복을 확인합니다.
  - 완료 증거: 격리된 시험값 왕복 성공과 키 식별 정보만 기록
- [ ] **작업자**: PostgreSQL 복귀 대상 이미지와 selector 값을 확인합니다.
  - 완료 증거: 복귀 커밋과 이미지가 실제로 존재하며 health 정상

**1단계 통과 조건:** 운영 서비스 변경 없이 모든 항목 성공. MongoDB 연결 실패가 있으면 여기서 중단합니다.

## 2. 데이터 최신화 준비

- [ ] **작업자**: 기존 C0/C1 백업과 격리 복원 증거가 현재도 유효한지 확인합니다.
- [ ] **작업자**: 롤백 이후 PostgreSQL에서 추가·수정·삭제된 범위를 계산합니다.
- [ ] **작업자**: 변경분 동기화 절차를 운영 쓰기 없이 dry-run으로 실행합니다.
- [ ] **작업자**: 모델별 건수, digest, 참조 관계, 삭제 대상 예상치를 대조합니다.
- [ ] **작업자**: 정규화 실패와 미매핑 데이터를 버리지 않고 검토 목록으로 남깁니다.

**완료 증거:** 모델별 비교 결과, 불일치 목록, 해결 여부. 고객명·담당자명·원문 값은 공개 저장소에 기록하지 않습니다.

**2단계 통과 조건:** 설명되지 않은 불일치 0건. 불일치가 남으면 실제 동기화를 실행하지 않습니다.

## 3. 핵심 업무 흐름 사전 검증

운영 데이터와 분리된 시험 데이터 또는 검증 전용 환경을 사용합니다. 운영 고객 데이터로 시험하지 않습니다.

- [ ] **작업자**: 운영 조회와 상세 조회가 PostgreSQL/MongoDB에서 같은 결과를 반환하는지 확인합니다.
- [ ] **작업자**: 일정·시간 저장과 다시 읽기를 확인합니다.
- [ ] **작업자**: OM 배정 preview와 저장을 확인합니다.
- [ ] **작업자**: 업무요청 저장을 확인합니다.
- [ ] **작업자**: Slack 알림 준비 상태와 시험 채널 실제 발송을 각각 확인합니다.
- [ ] **작업자**: 권한별 허용·거부 결과가 기존 PostgreSQL 동작과 같은지 확인합니다.
- [ ] **작업자**: 실패 로그에 원인 단계가 기록되고 개인정보·비밀은 기록되지 않는지 확인합니다.

**완료 증거:** 요청별 성공 결과, 저장 후 readback, Slack 시험 메시지 식별 정보, 오류 로그 0건.

**3단계 통과 조건:** 모든 흐름이 성공하고 기존 PostgreSQL 동작과 계약이 같아야 합니다.

## 4. 읽기 전환 리허설

- [ ] **작업자**: 기능군별 읽기 selector와 전환 순서를 확정합니다.
- [ ] **작업자**: 한 기능군만 MongoDB 읽기로 설정한 검증 배포를 수행합니다.
- [ ] **작업자**: health, 로그인, 대시보드, 운영 조회, 상세 조회를 확인합니다.
- [ ] **작업자**: 최소 30분 동안 연결·composition·권한 오류를 관찰합니다.
- [ ] **작업자**: PostgreSQL 읽기로 복귀하고 동일 기능이 정상인지 확인합니다.
- [ ] **작업자**: 나머지 기능군도 같은 방식으로 하나씩 반복합니다.

**4단계 통과 조건:** 모든 기능군의 전환과 복귀가 성공하고 사용자 오류가 없어야 합니다.

## 5. 최종 전환 승인

아래 항목은 책임자가 확인합니다. 이 승인 전에는 운영 쓰기를 중지하거나 selector를 바꾸지 않습니다.

- [ ] **책임자**: 1~4단계 완료 증거 확인
- [ ] **책임자**: 예상 쓰기 중단 시간 확인
- [ ] **책임자**: 전환 시작 시각과 업무 검증 담당자 확정
- [ ] **책임자**: `database-change-reviewed` 라벨 확인
- [ ] **책임자**: `database-cutover-approved` 라벨 확인
- [ ] **책임자**: 즉시 복구 기준과 복구 담당자 확인

## 6. 최종 동기화와 쓰기 전환

- [ ] **작업자**: 신규 쓰기를 제한하고 시작 시각을 기록합니다.
- [ ] **작업자**: 최종 PostgreSQL export 또는 delta·삭제 동기화를 수행합니다.
- [ ] **작업자**: 모델별 건수, digest, 참조 관계, sequence를 다시 대조합니다.
- [ ] **작업자**: 최종 복구 세트 A/B를 생성하고 각각 무결성·격리 복원을 확인합니다.
- [ ] **작업자**: 쓰기 selector를 **한 기능군만** MongoDB로 전환합니다.
- [ ] **작업자**: 저장·readback·권한·로그를 확인한 뒤 다음 기능군으로 진행합니다.
- [ ] **작업자**: 일정, OM 배정, 업무요청, Slack 알림을 실제 업무 검증 담당자와 확인합니다.

**즉시 복구 조건:** 새 5xx, 연결 실패, composition 실패, 데이터 불일치, 저장 후 readback 실패, 권한 계약 위반, Slack 누락 중 하나라도 발생한 경우.

## 7. 전환 후 확인

- [ ] **작업자**: 최소 30분 동안 오류율과 핵심 업무 로그를 관찰합니다.
- [ ] **작업자**: PostgreSQL 원본과 복구 이미지의 보존 상태를 확인합니다.
- [ ] **작업자**: 최종 selector, 배포 커밋, 검증 결과를 비밀 없이 기록합니다.
- [ ] **작업자**: 장애가 있으면 PostgreSQL로 먼저 복귀하고 `dev`와 `main`도 정상 트리로 영구 복구합니다.
- [ ] **책임자**: 실제 사용자 흐름 정상 확인 후 전환 완료를 승인합니다.

## 예상 시간

- 1~4단계 준비 검증: 약 1시간 30분~2시간 30분. 실패가 발견되면 수정 시간은 별도입니다.
- 5~7단계 최종 전환: 약 1시간. 이 중 예상 쓰기 중단은 15~30분입니다.
- 예상 시간을 넘기더라도 쓰기 중단 상태에서 원인을 수정하지 않습니다. 30분 안에 완료하지 못하면 PostgreSQL로 복귀합니다.
